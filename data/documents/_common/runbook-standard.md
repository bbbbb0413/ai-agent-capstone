# MSP 표준 장애 대응 런북

가상 데모 문서다. 모든 고객사·서비스에 공통으로 쓰는 장애 형태별 절차다.

고객 공지는 조치를 대신하지 않는다. 조치가 끝나고 보고서를 쓴 뒤 따로 승인을 받아 보낸다. 그래서 할 수 있는 조치가 있으면 조치를 먼저 제안한다.

조치는 세 단계로 정한다. (1) 이 문서로 장애 형태를 가리고 후보 조치를 정한다. (2) 서비스 목록(`get_service_inventory`)의 구조 정보로 후보 조치가 맞는지, 영향이 어떤지 검토한다. (3) 고객사 계약서의 허용 조치에 있는지 확인한다. 셋 중 하나라도 맞지 않으면 조치하지 않고 RB-STD-06을 따른다. 서비스별 주의 사항은 각 서비스 런북에 있다.

## RB-STD-01 설정 변경으로 인한 DB 커넥션 풀 고갈

- 증상: 5xx 에러율 급증, 로그에 `HikariPool-1 - Connection is not available, request timed out` 반복
- 구분: 최근 변경 이력에서 이상 시작 직전에 커넥션 풀 설정(`DEMO_POOL_SIZE`)이 줄었다. DB 자체 지연 로그(`slow query`)는 없다
- 구조 검토: DB 의존 대상의 상태가 정상인지 확인한다. DB가 지연·장애 상태면 RB-STD-05를 따른다
- 조치: 직전 배포로 롤백한다 (`rollback_deployment`)
- 직전 변경이 없으면 RB-STD-02의 재시작을 검토한다

## RB-STD-02 작업 스레드 고갈 (파드 멈춤)

- 증상: 5xx 에러율 급증, 로그에 `503 worker pool saturated`, `oldest worker blocked` 반복
- 구분: 이상 시작 직전에 배포·설정 변경이 없다. 프로세스 내부 상태 문제로 본다
- 구조 검토: 레플리카가 2개 이상이고 무상태면 하나씩 재시작해 중단 없이 처리한다. 레플리카가 1개면 재시작하는 동안 서비스 전체가 멈추므로, 제안 이유에 전체 중단 영향을 적는다. 재시작은 그대로 제안하고, 공지는 보고서 뒤에 보낸다. 상태 저장 서비스면 RB-STD-06을 따른다
- 조치: 파드를 재시작한다 (`restart_pods`)

## RB-STD-03 트래픽 급증 (앱 처리 용량 부족)

- 증상: 에러율은 정상인데 p95 응답시간 상승, 로그에 `request queue backlog` 경고 반복
- 구분: 5xx 에러가 늘지 않는다(늘면 RB-STD-02). 외부 API timeout 로그와 DB `slow query` 로그가 없다. 지연이 앱의 처리 대기에서 생긴다
- 구조 검토: 서비스 목록의 `autoscaling`(HPA)을 먼저 본다. 안전 상한(`safe_max_replicas`)은 DB 최대 연결 수와 계약 상한으로 정해지며, 넘으면 확장 때문에 DB 장애가 날 수 있다
  - HPA가 있고 최대치에 닿지 않았다(`atMax` false): HPA가 늘리는 중이다. 레플리카를 직접 바꾸지 않고 조치하지 않는다
  - HPA가 최대치에 닿았고 최대치가 안전 상한보다 작다(`canRaiseMax` true): HPA 최대치를 안전 상한까지 올린다
  - HPA가 최대치에 닿았고 최대치가 이미 안전 상한이다: 더 늘릴 수 없다. RB-STD-06을 따른다
  - HPA가 없다: 목표 레플리카는 현재의 2배이고, 안전 상한을 넘으면 상한까지만 늘린다. 이미 상한이면 RB-STD-06
- 조치: HPA가 있으면 `adjust_autoscaler`(`max_replicas`=안전 상한). HPA가 없으면 `scale_deployment`(`replicas`=목표 레플리카). HPA가 관리하는 서비스의 레플리카는 직접 바꾸지 않는다(HPA가 곧 덮어쓴다)

## RB-STD-04 외부 의존 서비스 지연

- 증상: p95 응답시간 상승, 로그에 `payment API timeout` 같은 외부 호출 경고 반복
- 구분: 지연이 외부 호출에 몰려 있고, 앱 처리 대기 경고와 DB 지연 로그는 없다
- 구조 검토: 의존 대상의 소유를 본다. 서드파티면 MSP가 고칠 수 없다. 고객사 소유 서비스면 그 담당 팀에 에스컬레이션한다
- 조치: 재시작·확장·롤백을 하지 않는다. 원인이 앱 밖에 있어서 효과가 없다. 고객 공지를 보낸다

## RB-STD-05 의존 대상(DB) 자체 장애

- 증상: p95 상승 또는 5xx, 로그에 `slow query ... took 1200ms (db=postgres)` 반복
- 구분: 앱의 커넥션 풀 설정은 그대로다. 지연이 DB 호출에서 생긴다
- 구조 검토: 앱 재시작·확장·롤백은 효과가 없다. 확장하면 DB 연결과 부하가 늘어 상황이 나빠진다
- 조치: 앱에 대한 조치를 하지 않는다. 의존 대상의 소유자(서비스 런북의 연락처)에게 에스컬레이션하고, 고객 영향이 있으면 공지한다

## RB-STD-06 계약·구조상 할 수 없는 조치가 필요할 때

- 해당: 위 조항의 조치가 고객사 계약의 허용 조치에 없을 때, 안전 상한에 이미 도달했을 때, 서비스 실행 환경이 그 조치를 지원하지 않을 때
- 조치: 조치하지 않는다. 담당 엔지니어와 고객사에 에스컬레이션하고, 고객 영향이 있으면 고객 공지도 보낸다
- 에스컬레이션 이유에 필요한 조치와 할 수 없는 이유(계약 조항, 상한 값)를 적는다

## RB-STD-07 원인을 확정하지 못했을 때

- 해당: 메트릭·로그·변경 이력으로 위 장애 형태 중 하나를 가리지 못했을 때
- 조치: 추측으로 조치하지 않는다. 담당 엔지니어에게 에스컬레이션한다
