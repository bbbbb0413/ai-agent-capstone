# A사 order-api 장애 대응 런북

가상 데모 문서다. 실제 고객사 문서가 아니다.

A사는 GitOps로 운영한다. 레플리카 수, 이미지, 설정값 같은 원하는 상태의 변경은 설정 저장소 PR로만 반영하고, A사 담당 엔지니어가 병합한다.

## RB-A-01 DB 커넥션 풀 고갈

- 증상: 5xx 에러율 급증, 로그에 `HikariPool-1 - Connection is not available, request timed out` 반복
- 확인: 최근 변경 이력에서 이상 시작 직전에 커넥션 풀 설정(`DEMO_POOL_SIZE`)이 바뀌었는지 본다
- 1차 조치: 직전 변경으로 풀 크기가 줄었으면 직전 배포로 롤백한다 (`rollback_deployment`). 설정 저장소에 되돌리기 PR이 만들어진다
- 2차 조치: 직전 변경이 없으면 파드를 재시작한다 (`restart_pods`)
- 승인: 담당 MSP 엔지니어 (롤백 PR 병합은 A사 GitOps 절차를 따른다)

## RB-A-02 트래픽 급증으로 인한 응답 지연

- 증상: p95 응답시간 1초 초과, 에러율은 정상, 외부 의존(DB, 결제)의 지연 로그 없음
- 조치: 레플리카를 현재의 두 배(최대 6)로 확장한다 (`scale_deployment`). 설정 저장소에 확장 PR이 만들어진다
- 원인이 외부 의존이면 확장하지 않고 고객사 공지를 먼저 보낸 뒤 담당자에게 에스컬레이션한다

## RB-A-03 고객 공지 기준

- Gold 등급이므로 장애 인지 후 15분 안에 첫 공지를 보낸다
- 공지 문안에는 영향 범위, 현재 상태, 다음 안내 시각을 넣고 원인 추측은 넣지 않는다
