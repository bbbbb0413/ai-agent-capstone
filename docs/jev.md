# Jev 장애 형태 판정

> 작성일: 2026-10-22 · 기준 커밋: `3c27033` 이후 · 상태: **2단계 완료 (GPT와 하이브리드로 Agent 흐름에 연결, 실제 장애 `b-hang` 통과)**

[TypeSafe](https://typesafe.ai)의 Jev로 장애 형태(공통 런북 조항 RB-STD-01~07)를 고르는 기능을 시험한 기록이다. 변경 요약은 [기능별-변경사항.md](기능별-변경사항.md) 14장, 테스트 케이스는 같은 문서 T14에 있다.

## 1. Jev가 무엇인가

- TypeSafe의 System One 모델이다. 글을 생성하지 않고, 미리 정한 선택지 중 하나를 확률·확신도와 함께 고른다.
- 답이 항상 선택지 안에 있어서 파싱 실패나 엉뚱한 답이 없다. 숫자 계산과 날짜 비교에는 약하다(공식 문서).
- API: `POST https://api.typesafe.ai/v1/systemone`. Python SDK는 `typesafe-sdk`. 이번 시험은 `jev-latest`(= `jev-1.13.0`)를 썼다.
- 요금: 입력 100만 토큰당 0.042달러, 출력 무료([Models](https://docs.typesafe.ai/models), 2026-10-22 확인).

## 2. 어디에 반영했나

### 역할 나누기 (하이브리드)

| 누가 | 무엇을 |
|---|---|
| 코드 | 지표·로그 신호·직전 변경 조회, 숫자를 기준과 비교한 글로 변환 |
| **Jev** | **장애 형태(조항) 하나 고르기**만. 0.2초 |
| GPT | 조치 종류, 인자(서비스, 레플리카 수, 에스컬레이션 분류), 이유 글, 고객 공지 문안 |
| 코드 | GPT가 고른 조치가 조항·계약·구조에 맞는지 검사 (`_clause_mismatch` 등, 바꾸지 않음) |

```
diagnose ──(signals)──▶ retrieve_runbook ──▶ propose_action
                                              ├─ 서비스 목록 조회 ─┐ 동시에
                                              ├─ Jev 판정 ─────────┘
                                              ├─ RB-STD-01~05이고 확신도 ≥ 0.9 → GPT 입력 맨 앞에 "장애 형태(Jev 판정, 확신도 99%): RB-STD-05"
                                              │  RB-STD-07, 확신도 < 0.9, 실패 → GPT 입력은 그대로 (GPT가 판정표로 직접 고른다)
                                              ├─ 판정을 STEP 이벤트로 기록 → 작업 진행 타임라인 "장애 형태 판정 (Jev)"
                                              └─ GPT가 조치를 고른다 → 조치 검사 → 승인
```

### 안전장치

- 키가 없으면 Jev를 부르지 않는다. 팀원 환경에서 키 없이 돌려도 동작은 전과 같다.
- Jev가 실패하거나 5초 안에 답하지 않으면 판정 없음으로 두고 GPT가 지금처럼 고른다. 서비스 목록 조회와 동시에 돌려서 평소에는 기다리는 시간이 늘지 않는다.
- Jev 판정은 GPT에 주는 입력일 뿐이다. 조치가 조항·계약·구조에 맞는지는 코드가 그대로 검사하고, 사람이 승인한다.
- **Jev의 RB-STD-07(원인 미확정)은 GPT에 넘기지 않는다.** Jev는 코드가 센 신호 건수만 보고, GPT는 로그 원문 요약까지 본다. 신호가 비어 Jev가 07을 고르면 "원인 미확정"이 아니라 "센 신호가 어느 조항과도 맞지 않는다"일 뿐이다. 실제 장애에서 이 판정이 GPT를 덮어써 재시작 대신 원인 미확정 에스컬레이션이 나간 적이 있다(4장).

### 판정 방식

1. **입력 변환 (`build_state`):** Jev는 숫자 비교에 약해서, 코드가 기준과 비교한 결과를 글로 넘긴다.

   | 신호 | 기준 | 넘기는 글 예 |
   |---|---|---|
   | 5xx 에러율 | 5% (`_signal_clause`와 같음) | `높음 (46.0%, 기준 5% 이상)` |
   | p95 응답시간 | 1초 (`P95_THRESHOLD_SECONDS`) | `느림 (2.10초, 기준 1초 이상)` |
   | 로그 신호 5종 | 0건이면 없음 | `DB 지연 (slow query)`: `31건` |
   | 직전 배포·설정 변경 | `_recent_change` 결과 | `있음` / `없음` / `알 수 없음` |

2. **질문:** 선택지 하나. RB-STD-01·02·03·04·05·07과 각 조항의 증상·구분(공통 런북 요약). RB-STD-06은 장애 형태가 아니라 "조치를 할 수 있는가"에 관한 조항이라 뺐다.
3. **결과:** `{"choice", "confidence", "probabilities"}`. Jev가 실패하거나, 5초 안에 답하지 않거나, `TYPESAFE_API_KEY`가 없으면 예외 없이 `None`(판정 없음)이다.

## 3. GPT와 비교

### 방법

- 장애 7가지 × 3번 = 21번. 입력(`build_state` 결과)과 선택지(`FAULT_CRITERIA`)는 셋 모두 같다.
- GPT는 Agent와 같은 모델이다. `gpt-5-mini`(Agent 기본 모델)와 `gpt-5-nano`(대체 모델), 구조화 출력(`with_structured_output`). 추론 강도는 Agent 기본값 `low`와, 조치 제안 단계가 실제로 쓰는 `medium`(`harness.PROPOSE_REASONING_EFFORT`) 두 가지로 쟀다. 요청은 하나씩 차례로 보냈다.
- 시간은 요청부터 응답까지(네트워크 포함). 토큰은 각 API가 돌려준 사용량이다.

### 결과 (2026-10-22)

| 모델 | 정답 | 평균 시간 | 최대 시간 | 입력 토큰 | 출력 토큰 (그중 추론) | 1회 비용 (USD) | 1만 회 비용 |
|---|---|---|---|---|---|---|---|
| **Jev** (`jev-1.13.0`) | 21/21 | **0.18초** | 0.40초 | 856 | 94 (0) · 과금 안 함 | **0.000036** | **0.36달러** |
| `gpt-5-mini`, `medium` (조치 제안 단계 설정) | 21/21 | 3.03초 | 4.80초 | 565 | 191 (168) | 0.000522 | 5.22달러 |
| `gpt-5-mini`, `low` (Agent 기본값) | 21/21 | 2.13초 | 4.02초 | 565 | 72 (49) | 0.000285 | 2.85달러 |
| `gpt-5-nano`, `low` (대체 모델) | 21/21 | 1.69초 | 2.39초 | 565 | 133 (110) | 0.000081 | 0.81달러 |

- **속도:** 조치 제안 단계와 같은 설정(`gpt-5-mini`, `medium`)보다 Jev가 약 17배 빠르다. Jev는 모든 호출이 0.4초 안이었다.
- **토큰:** 입력은 Jev가 더 많다(856 대 565). 선택지 설명을 질문 형식으로 넘기는 몫이다. 출력은 Jev만 과금하지 않는다. GPT는 같은 질문에도 추론 토큰을 0~256개로 들쭉날쭉 쓰고, `medium`이면 평균 168개로 늘어난다.
- **비용:** 1회당 Jev가 조치 제안 단계 설정의 약 1/14, `gpt-5-mini low`의 약 1/8, `gpt-5-nano`의 약 1/2이다.
- **정확도:** 셋 다 21/21이다. 이번 입력은 선택지 설명과 거의 그대로 맞는 쉬운 경우라 정확도로는 차이가 나지 않았다.
- **같은 입력 일관성:** Jev는 3번 모두 같은 답과 같은 토큰 수였다. GPT도 답은 같았지만, 추론 토큰 수와 시간은 매번 달랐다.

### 실제 Agent 흐름의 GPT 시간과 구분해야 한다

실제 작업에서 조치 제안 단계는 훨씬 오래 걸렸다. 아래 값은 `app.task_events`에서 서비스 목록 조회가 끝난 뒤 GPT가 조치 도구를 부르기까지 걸린 시간이다(2026-10-20 작업 4건).

| 작업 | 시간 | GPT가 고른 것 |
|---|---|---|
| `63493c3b` | 128.3초 | 조치 실행 요청 |
| `5cd1f520` | 72.3초 | 조치 실행 요청 |
| `38ec4155` | 23.4초 | 에스컬레이션 |
| `b60cef02` | 18.2초 | 조치 실행 요청 |

이 시간은 **조항 고르기만이 아니라** 진단 대화 전체, 런북·계약 조항, 서비스 목록을 읽고 조치와 인자(서비스, 레플리카 수, 이유 글)를 정하는 시간이다. 조항이 맞지 않아 되돌려 보낸 재시도도 들어 있다. 그래서 위 표의 2초와 직접 비교하면 안 된다.

Jev가 맡은 것은 이 중 **장애 형태를 고르는 부분**이다. 조치 인자와 이유 글은 여전히 GPT가 쓴다. 기대 효과는 조항을 Jev가 먼저 정해 주면 GPT가 판정표를 따져 보는 추론이 줄고, 조항 불일치로 되돌려 보내는 재시도가 줄어드는 것이다. 조치 제안 단계 전체가 얼마나 빨라지는지는 실제 작업으로 재야 한다(7장).

## 4. 실제 장애 테스트 (2026-10-22)

`python3 scripts/e2e.py b-hang --no-branch`. B사 reservation-api에 작업 스레드 멈춤(`WORKER_HANG`)을 넣었다. 정답은 RB-STD-02, 조치는 재시작이다.

| 실행 | Jev 판정 | GPT 조치 | E2E |
|---|---|---|---|
| 1차 (`6c8972aa`) | **RB-STD-07, 확신도 0.99** → GPT에 넘김 | 원인 미확정 에스컬레이션 (재시작 안 함) | **실패** |
| 2차, 아래 두 가지 수정 후 (`61f3eb73`) | RB-STD-02, 확신도 1.00 → GPT에 넘김 | `restart_pods` → 회복 확인 RECOVERED | **통과** (170초) |

**1차 실패 원인: 로그 신호 집계 버그 (Jev 이전부터 있던 버그).** `_recent_log_patterns`는 로그를 묶을 때 숫자를 `#`으로 바꾼다(`order rejected: # worker pool saturated …`). 그런데 신호 문구 `503 worker pool saturated`는 숫자를 그대로 둔 채 찾아서, **작업 스레드 고갈 신호가 늘 0건**이었다. 다섯 신호 중 문구에 숫자가 있는 것은 이것뿐이다. GPT는 로그 원문 요약을 읽어 RB-STD-02를 스스로 찾았기 때문에 그동안 드러나지 않았다. Jev는 건수만 보고 "맞는 신호 없음 → RB-STD-07"을 확신했고, 그 판정이 GPT 입력에 들어가 GPT가 따랐다. 같은 입력을 다시 넣어 보면 신호 건수가 0일 때만 RB-STD-07(1.00)이 나오고, 건수가 있으면 RB-STD-02(0.98~1.00)다.

**수정:**
1. 신호 문구에도 같은 숫자 치환을 적용해 찾는다 (`graph.py` `_recent_log_patterns`, 한 줄). `_signal_clause`의 RB-STD-02 판정도 이제 동작한다.
2. Jev의 RB-STD-07은 GPT에 넘기지 않고 기록만 한다 (2장 안전장치).

**2차 측정값 (실행 1건이라 참고만):**
- Jev 판정은 서비스 목록 조회와 동시에 돌았다. 목록 조회가 끝난 뒤 Jev를 기다린 시간은 0.14초다.
- Jev 판정부터 GPT가 조치를 고르기까지 11.5초. 이전 실제 작업의 조치 제안 단계는 18~128초였지만 장애 종류와 실행 조건이 달라 직접 비교하지 않는다.
- 작업 진행 타임라인에 "장애 형태 판정 (Jev): RB-STD-02 · 확신도 100% · 조치 판단에 사용"이 보인다 (`output/captures/jev-timeline.png`).

**배운 것:** Jev는 받은 입력 안에서는 정확하지만, 입력이 틀리면 틀린 답을 높은 확신도로 낸다. 확신도는 "입력이 맞다면"의 확신이다. 그래서 Jev 입력(코드가 센 신호)이 GPT 입력(로그 원문)보다 좁은 이상, "판단 근거 없음"류의 답은 GPT를 덮어쓰지 않게 했다.

## 5. 시험하며 찾은 다른 것

**`_signal_clause`가 DB 지연을 놓친다.** 커넥션 풀 고갈 로그와 DB 지연(`slow query`) 로그가 같이 있으면 `_signal_clause`는 RB-STD-01(롤백)로 판정한다. Jev와 GPT는 모두 RB-STD-05(DB 장애)로 판정했다. 공통 런북 RB-STD-01의 구분은 "DB 자체 지연 로그는 없다", 구조 검토는 "DB가 지연·장애 상태면 RB-STD-05를 따른다"이므로 RB-STD-05가 맞다. `_signal_clause`의 RB-STD-01 조건에 `slow_query`가 없는지 보는 부분을 넣어야 한다. 팀원과 확인한 뒤 고친다.

## 6. 한계

- 시험한 7가지는 선택지 설명과 거의 그대로 맞는 경우다. 섞인 경우의 정답도 선택지 설명에 적어 두었다("커넥션 풀 고갈 로그가 같이 있어도 DB 지연이 있으면 이 조항"). 어려운 경우의 정확도는 아직 모른다.
- Jev 확신도는 대부분 1.00이었다(DB 지연만 0.99). 확신도가 실제 정답률과 맞는지(보정)는 실제 작업에서 판정을 모아 봐야 한다.
- 비용 비교는 같은 질문 하나 기준이다. 실제 조치 제안 단계의 GPT 토큰은 기록하지 않아서 비교하지 못했다.
- Jev는 외부 서비스다. 고객사 지표와 로그 신호 건수가 TypeSafe로 나간다. 로그 원문은 보내지 않는다.

```bash
cd server/python/agent
uv run --with pytest --with pytest-asyncio pytest -q tests/test_jev.py         # 단위 (키 불필요)
uv run --with typesafe-sdk python scripts/jev_probe.py --repeat 3              # Jev 실측
uv run --with typesafe-sdk python scripts/jev_vs_gpt.py --repeat 3             # GPT 비교 (약 1분 30초)
```

- 키는 저장소 루트 `.env`의 `TYPESAFE_API_KEY`, `OPENAI_API_KEY`에서 읽는다. `.env`는 git에 올리지 않는다.
- 설정: `TYPESAFE_MODEL`(기본 `jev-latest`), `TYPESAFE_TIMEOUT_SECONDS`(기본 5초), `TYPESAFE_MIN_CONFIDENCE`(기본 0.9).
- 플랫폼에 반영: `.env`에 `TYPESAFE_API_KEY`를 넣고 `docker compose up -d --build agent frontend`. Jev를 끄려면 키를 비우고 같은 명령.
