# 장애 처리 흐름: 알림부터 종료까지

알림이 울린 순간부터 인시던트가 닫힐 때까지 무엇이 어떤 순서로 일어나는지, 각 단계에서 누가 판단하는지 정리한다. 한 서비스에 원인이 여럿 겹친 경우를 포함한다.

- **[코드]** 정해진 규칙대로 동작한다 (조회, 정리, 라우팅, 검사). 판단하지 않는다
- **[에이전트]** LLM이 판단한다 (원인 후보, 순위, 조치, 회복 여부)
- **[사람]** 승인한다

기준: [SPEC-compound-faults](specs/SPEC-compound-faults.md). 그래프는 `server/python/agent/src/agent/graph.py`의 `build()`다.

원칙: **코드는 사실을 조회해 원인 후보별로 정리하고, 원인 후보와 순위는 에이전트가 판단하며, 코드는 명백한 위반만 막는다.** 순위가 판단 기준과 달라도 막지 않고 기록하며, 맞는지는 E2E가 판정한다.

## 1. 전체 흐름

```
① 장애 발생 (예: order-api 파드 멈춤 + 외부 결제 지연)
   │
② [코드] Prometheus 알림 규칙 (infra/prometheus/alert-rules.yml)
   │   HighErrorRate: 에러율 > 20%, HighLatency: p95 > 1초. 둘 다 15초 넘게 지속되면 발생
   │   rate[30s], 평가 주기 5초 → 장애 시작부터 약 40초 뒤 (데모 환경 값, SPEC-e2e-speed ⑤)
   │
③ [코드] Alertmanager → backend 웹훅 (서비스마다 묶음, group_wait 5초, 해제 알림은 20초마다)
   │   같은 (고객사, 서비스)에 열린 인시던트, 또는 진단 작업이 아직 진행 중인 인시던트가 있나?
   │   (두 알림이 동시에 와도 하나만 열리게 고객사·서비스마다 잠근다)
   │   - 없음 → 인시던트 생성 + 알림 기록(incident_alerts) + DIAGNOSE 작업 생성
   │   - 있음 → 새로 만들지 않는다
   │            · 기존 인시던트에 알림을 덧붙인다 (닫혀 있었으면 다시 연다)
   │            · 심각도가 더 높으면 올린다 (warning → critical)
   │            · 진행 중인 작업에 "알림 추가" 이벤트를 남긴다 (작업은 새로 만들지 않는다)
   │   → 한 서비스에는 인시던트 하나, 작업 하나만 돈다
   │
④ [코드] 작업 전달
   │   task_outbox → Kafka → agent kafka_worker가 작업을 받아 그래프를 실행한다
   │
⑤ [코드] intake → load_context
   │   고객사 정보, 서비스 목록(계약상 가능한 조치 supportedActions, 확장 상한 safeMaxReplicas,
   │   HPA 상태, 관측 정의 observability, 의존 대상 dependencies), SLA, 인시던트 정보를 조회한다
   │
⑥ [코드] route_triage
   │   인시던트 심각도가 P1이면 → ⑦ / 아니면 → ⑧
   │   (질문 작업은 문서 질문 → 런북 검색, 열린 인시던트 없음 → 이상 없음 등 다른 길로 간다)
   │
⑦ [코드→사람] escalate (P1만)
   │   담당자 호출(에스컬레이션) 승인 요청 → 작업 상태 WAITING_APPROVAL
   │   [사람] 엔지니어 승인 → 발송 대기열 등록 → ⑧로 계속
   │
⑧ diagnose (진단)
   │   [코드] 미리 조회한다
   │     - Loki 로그: 인시던트 시작 2분 전부터(최대 10분), 반복 메시지별 건수.
   │       같은 서비스의 직전 인시던트가 그 사이에 닫혔으면 그 뒤부터 (앞 장애 로그가 섞이지 않게)
   │     - 로그 신호 5개의 건수와 처음 나온 시각 (신호마다 Loki 집계, 5초 구간. 200줄 요약에 묻히지 않는다)
   │     - 지표: 에러율, p95, 초당 요청 수 (최근 1분, 이 서비스만)
   │     - 의존 대상(DB, 외부 API)마다 상태(HEALTHY·DEGRADED·DOWN)와 p95
   │     - 최근 배포·설정 변경, 직전 변경 여부(인시던트 시작 전 15분 안)
   │     - 과거 유사 회고
   │   [코드] cause_facts: 위 값을 원인 후보(RB-STD-01~05)별 사실 표로 정리한다
   │     조항 | 신호 건수 | 처음 나온 시각 | 의존 대상 상태 | 의존 대상 비율(그 p95 / 요청 p95) | 근거 있음
   │     순위와 흡수는 정하지 않는다
   │   [코드] 다시 진단이면 처리한 원인(handled)과 그 신호의 지금 건수를 함께 준다
   │   [에이전트] 사실 표를 보고, 필요하면 도구를 더 부른다
   │     → 판단 기준(2장)에 따라 원인 후보, 증상으로 볼 후보, 순위를 정하고 근거를 쓴다
   │     → 출력:
   │         이상 시작 / 근거 / 직전 변경
   │         원인 후보: 1) RB-STD-0x … 2) RB-STD-0y …
   │         처리할 원인: RB-STD-0x
   │         병목: 앱|DB|외부
   │   [코드] 출력의 "원인 후보", "처리할 원인" 줄을 읽어 causes, target_clause에 둔다
   │     형식이 깨져 읽지 못하면 검사 없이 진행하고 기록만 남긴다
   │   [코드] 근거가 된 도구 호출이 하나도 없으면 "원인 미확정"으로 바꾼다
   │
⑨ [코드] route_diagnose
   │   "원인 미확정"이면 → 보고서(⑯) / 아니면 → ⑩
   │
⑩ [코드] retrieve_runbook
   │   진단 결과로 공통 런북, 고객사 런북, 계약(허용 조치) 조항을 검색한다
   │
⑪ propose_action (조치 제안)
   │   [코드] Jev가 장애 형태를 판정한다. 처리할 원인과 다르면 기록만 하고 에이전트에 전달하지 않는다
   │   [에이전트] 진단이 정한 처리할 원인의 조치 도구 하나를 고른다 (장애 형태를 다시 고르지 않는다)
   │     재시작 / 확장 / 롤백 / HPA 최대치 / 에스컬레이션 / 고객 공지
   │   [코드] action_guards.first_problem 검사. 문제가 있으면 이유와 함께 돌려보낸다 (최대 2번)
   │     ① 처리할 원인에 근거가 없다 (사실 표의 "근거 있음"이 false)
   │     ② 이미 앱 조치를 한 원인에 앱 조치를 또 한다 (같은 원인의 에스컬레이션은 된다)
   │     ③ 제안한 조치가 처리할 원인을 고치는 조치도, 그 조항의 에스컬레이션·공지도 아니다
   │     - 인용한 런북 조항과 조치가 맞지 않는다
   │     - 계약·실행 환경상 할 수 없는 조치다
   │     - ACTION_BLOCKED의 required_action이 처리할 원인의 조치와 다르다
   │     - 확장 방식이 서비스 구조와 맞지 않는다
   │   [코드] 순위는 막지 않는다. 원인 후보, 처리할 원인, 사실 표를 작업 이벤트에 기록한다
   │   HPA가 아직 확장 중이면 도구를 부르지 않고 이유만 적는다 → 보고서(⑯)
   │
⑫ [코드→사람] approval
   │   승인 요청 → WAITING_APPROVAL → [사람] 승인 또는 거절
   │   (자동 승인 설정이 켜져 있으면 backend가 승인한다)
   │   거절이면 → 보고서(⑯)
   │
⑬ [코드] execute → business-mcp → backend
   │   [코드] backend가 한 번 더 막는다: 안전 상한, 계약, 실행 환경 (422)
   │   [코드] 앱 조치를 실행하면 처리한 원인을 handled에 쌓는다 {조항, 조치, 신호, 조치 전 신호 건수, 시각}
   │   - DIRECT 고객사(B사): K8s에 바로 실행 → EXECUTED → ⑮
   │   - GITOPS 고객사(A사): 설정 저장소에 PR 생성 → PR_CREATED → ⑭
   │   - 에스컬레이션·고객 공지, 실행 실패: 회복 확인 없이 바로 보고서(⑯)
   │
⑭ [코드→사람] await_change (PR일 때만)
   │   [사람] PR 병합 → ArgoCD 동기화
   │   SYNCED면 → ⑮ / 아니면 → 최종 에스컬레이션
   │
⑮ verify (회복 확인)
   │   [코드] 반영을 기다린 뒤 조치한 서비스의 에러율·p95를 잰다 (15초 창). 기준 안이면 한 번 더 잰다
   │   [에이전트] 수치를 보고 RECOVERED / NOT_RECOVERED를 판단한다
   │   [코드] 다시 잰 값이 기준을 넘으면 에이전트가 회복이라 해도 NOT_RECOVERED
   │   [코드] 미회복이면 처리한 원인의 신호를 조치 뒤 구간으로 다시 센다
   │          (signal_count_after, 조치 전의 20% 미만이면 cleared)
   │   [코드] route_verify
   │     - 회복 → ⑯
   │     - 미회복, 다시 진단한 적 없음 → ⑧ 다시 진단
   │         [에이전트] 신호가 사라졌으면 다음 원인을, 남아 있으면 같은 원인의 에스컬레이션을 고른다
   │         [코드] 같은 원인에 앱 조치를 또 하면 ⑪ 검사 ②가 돌려보낸다
   │     - 미회복, 이미 한 번 다시 진단함 (조치 최대 2개)
   │         → 최종 에스컬레이션(NOT_RECOVERED, 처리하지 못한 원인 후보를 사유에 적는다) → ⑯
   │
⑯ report
   │   [에이전트] 보고서를 스트리밍으로 쓴다
   │     - "원인 후보" 절: 순위, 조항, 근거, 증상으로 본 후보, 처리 여부.
   │       판단 기준과 다른 순위였으면 그 근거
   │   [에이전트] 요약 분류: 처리한 원인(cause), 나머지 원인(other_causes), 근거 조항
   │
⑰ [코드→사람] notice_approval
   │   보고서에 고객 공지 문안이 있고 아직 보내지 않았으면 [사람] 관리자 승인 → 발송
   │
⑱ [코드] 묶인 알림이 모두 해제되면 인시던트 RESOLVED
```

## 2. 원인 판단 기준 (에이전트, `prompts/diagnose.md`)

코드가 강제하지 않는다. 에이전트가 이 기준으로 판단하고, 다르게 정하려면 근거를 적는다.

### 2.1 증상으로 볼 후보

아래 계층의 원인이 위 계층의 증상을 설명하면, 위 계층 후보는 독립 원인이 아니라 증상으로 적는다.

| 증상으로 볼 후보 | 원인 후보 | 조건 | 이유 |
|---|---|---|---|
| RB-STD-01 풀 고갈 | RB-STD-05 DB 지연 | 직전 설정 변경이 **없을 때** | 느린 쿼리가 커넥션을 오래 잡는다 |
| RB-STD-03 트래픽 급증 | RB-STD-04, 05 | 그 의존 대상 비율이 0.5 이상 | 의존 호출이 처리 시간을 차지한다 |
| RB-STD-03 트래픽 급증 | RB-STD-02 | 항상 | 묶인 작업 스레드가 대기열을 만든다 |

직전 설정 변경이 있으면 풀 고갈은 증상으로 보지 않는다. 풀 크기를 줄인 배포와 DB 지연이 함께 있으면 두 원인 모두 진짜다.

### 2.2 처리 순서

1. 근거가 지표와도 맞는 원인 > 로그 신호만 있는 원인 > 의존 대상 상태만 있는 원인
2. **바로 고칠 수 있는 앱 원인 먼저:** RB-STD-01·02·03(앱 조치) > RB-STD-05(DBA 에스컬레이션) > RB-STD-04(고객 공지). 앱 원인을 먼저 고치면 남은 증상이 외부·DB 원인 하나로 좁혀진다. 외부·DB 후보는 처음부터 보고서와 진행 화면에 보인다. 앱 조치가 계약상 불가해도 순위는 그대로이고, 조치는 그 조치의 승인 요청(`ACTION_BLOCKED`)이 된다.
3. 먼저 시작한 쪽 (신호가 처음 나온 시각)
4. 신호 건수가 많은 쪽

### 2.3 장애 형태별 조치

| 조항 | 조치 | 구분 |
|---|---|---|
| RB-STD-01 풀 고갈 | 롤백 (직전 변경이 없으면 재시작) | 앱 |
| RB-STD-02 작업 스레드 고갈 | 재시작 | 앱 |
| RB-STD-03 트래픽 급증 | 확장 (HPA면 최대치 올리기) | 앱 |
| RB-STD-05 DB 지연 | DBA 에스컬레이션 | DB |
| RB-STD-04 외부 의존 지연 | 고객 공지 | 외부 |
| RB-STD-06 | 조치를 할 수 없을 때 `ACTION_BLOCKED` 에스컬레이션 | |
| RB-STD-07 원인 미확정 | 에스컬레이션 | |

## 3. 누가 판단하나

| 판단 | 누가 | 위치 |
|---|---|---|
| 장애가 났는지 | [코드] 알림 규칙 | `infra/prometheus/alert-rules.yml` |
| 인시던트를 새로 만들지 | [코드] 같은 (고객사, 서비스)에 열린 인시던트가 있는지 | backend 알림 웹훅 |
| 로그·지표·의존 대상·변경 조회 | [코드] | `signals.observe`, `graph.diagnose` |
| 원인 후보별 사실 정리 | [코드] 순위·흡수는 정하지 않는다 | `signals.cause_facts` |
| **원인 후보, 증상으로 볼 후보, 순위, 처리할 원인** | **[에이전트]** 판단 기준(2장) | `prompts/diagnose.md` |
| **조치** | **[에이전트]** 처리할 원인의 조치 | `graph.propose_action`, `prompts/propose.md` |
| 조치가 명백히 틀렸는지 | [코드] 검사 ①②③ 외, 돌려보내기 | `action_guards.first_problem` |
| 실행해도 되는지 (안전 상한·계약·실행 환경) | [코드] backend 422 | backend 실행 API |
| 실행할지 | [사람] 승인 | `graph.approval`, 자동 승인 설정 |
| 회복됐는지 | [에이전트]가 판단, [코드]가 측정값으로 뒤집을 수 있음 | `graph.verify` |
| 미회복 뒤 다음 원인을 처리할지, 같은 원인을 에스컬레이션할지 | [에이전트] 코드가 다시 센 신호를 보고. 같은 원인의 앱 조치는 [코드]가 막는다 | `graph.diagnose`, `action_guards.target_already_handled` |
| 다음에 어디로 갈지 | [코드] 라우팅 | `route_*` |
| 순위가 기준대로였는지 | E2E | `scripts/e2e.py` |

## 4. 예: 파드 멈춤 + 외부 결제 지연 (A사 order-api)
