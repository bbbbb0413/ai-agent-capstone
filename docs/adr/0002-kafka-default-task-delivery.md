# ADR 0002: 작업 전달은 Kafka를 기본으로 하고, 유실·중복을 DB로 막는다

- 상태: **채택됨** (2026-10-20, 코드 반영 완료)
- 관련 문서: [SPEC-kafka-scale](../specs/SPEC-kafka-scale.md), [기획안](../OpsLens-기획안.md) 4.1절·8장

## 배경

처음에는 HTTP(backend가 agent `/run`을 바로 호출)가 기본이고 Kafka는 가산점용 선택 경로였다. Kafka 경로는 단일 소비자를 전제로 해서, 브로커 일시 장애나 소비자를 여러 개로 늘릴 때 다음이 깨졌다(스펙 1장).

- 발행 결과를 기다리지 않아 브로커가 잠깐 멈추면 작업이 QUEUED로 남았다.
- 한 묶음을 동시에 돌려 같은 고객사 작업의 순서가 깨지고, 재시도 대기(`sleep`)가 새 Gold 작업까지 막았다.
- 리밸런싱으로 다시 받은 미완료 작업을 "중복"으로 버렸다.

## 결정

1. **Kafka가 기본 작업 전달 방식이다.** compose 기본값이고 프로필 없이 함께 뜬다. HTTP는 `DISPATCH_MODE=http`로 남긴다(Kafka 없이 원인을 좁힐 때).
2. **발행은 Transactional Outbox로 한다.** 작업과 전달 대기열(`task_outbox`)을 한 트랜잭션에 쓰고, Relay가 커밋 직후와 1초마다 발행한다. 5번 실패하면 작업을 FAILED로 끝낸다.
3. **소비는 등급별 그룹, 파티션 단위 순서, 레코드 단위 커밋이다.** 실행 슬롯은 HTTP 재개와 공유하고 Gold가 기다리면 Silver가 양보한다.
4. **실행 여부는 DB 임대로 정한다.** 실행하는 파드가 `task_budget`에 소유자와 갱신 시각을 남긴다. 임대가 살아 있으면 다른 파드가 같은 작업을 돌리지 않고, 끊기면 checkpoint에서 이어 간다.
5. **agent 스키마는 기동 때 만들지 않는다.** 1회성 `agent-migrate`(Alembic)가 먼저 실행한다.

## 검토했지만 택하지 않은 안

| 안 | 택하지 않은 이유 |
|---|---|
| HTTP를 기본으로 유지 | 동시 알림을 흡수하는 대기열과 SLA 등급별 우선 처리가 없다. 발표·평가 경로와 기본 경로가 달라진다 |
| `kafka.send().get()`만 추가 (Outbox 없이) | DB 커밋 직후 backend가 죽으면 여전히 유실된다 |
| Debezium CDC, Redis 분산 락 | 새 외부 인프라가 늘어난다. PostgreSQL만으로 같은 보장을 낼 수 있다 |
| 프로세스 안의 실행 중 목록으로 중복 판정 | 파드를 늘릴 때의 리밸런싱은 실행 중인 파드가 살아 있어도 파티션을 넘긴다. 다른 파드가 같은 작업을 동시에 돈다 |

## 결과

- 브로커가 20초 멈췄다 살아나도 작업이 이어지고, 계속 멈춰 있으면 약 1분 뒤 FAILED가 된다(실측).
- 실행 파드를 죽이고 다시 띄우지 않아도 약 90초 뒤 다른 파드가 이어 간다(실측).
- 비용: 같은 파티션의 작업은 순서대로 돌아, 한 고객사의 인시던트 작업이 승인 대기에 닿을 때까지 같은 파티션의 질문 작업이 기다린다. 임대(60초)가 끊긴 뒤에야 이어 가므로 파드 장애 시 그만큼 늦어진다.
