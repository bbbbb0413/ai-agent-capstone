## 1. 인증·권한

**문제:** 로그인 쿠키는 브라우저의 모든 탭이 같이 쓴다. 다른 탭에서 다른 계정으로 로그인하면 화면 표시(예: admin)와 실제 권한(예: engineer)이 달라져 승인·거절이 403으로 실패했다. 쿠키가 만료돼도 화면은 로그인 상태로 남았고, 로그아웃해도 쿠키가 남았다.

**변경:**
- `GET /api/auth/me`: 쿠키 기준 실제 사용자를 돌려준다.
- `POST /api/auth/logout`: 서버가 쿠키를 즉시 만료시킨다 (`Max-Age=0`). 로그인 없이 호출할 수 있다.
- 화면 이동, 탭 복귀 때 `/me`로 화면 표시를 실제 사용자에 맞춘다 (`session.sync()`).
- 어떤 API에서든 401이 오면 세션 표시를 지우고 로그인 화면으로 보낸다 (`api.js`의 `setUnauthorizedHandler`).
- 역할별 화면 제한:
  - 고객사 담당자(`TENANT_VIEWER`)는 포털(`/portal`) 밖 주소로 들어가면 포털로 돌려보낸다 (`router.js`).
  - 관리자 전용 승인 도구는 엔지니어에게 버튼을 숨긴다 (3장).

**코드:** `AuthController.java`, `SecurityConfig.java`, `front/src/api.js`, `session.js`, `main.js`, `router.js`, `App.vue`.

**한계:** 고객사 담당자의 포털 제한은 화면 라우팅에서만 한다. backend 작업 API는 고객사 담당자도 자기 고객사 범위 안에서 호출할 수 있다.

## 2. Agent 작업 실행

### 2.1 시나리오 A 통과 조정

시나리오 A(A사 DB 커넥션 풀 고갈)가 120초 한도 초과, 조치 도구 미호출, 회복 오판으로 끝까지 가지 못해 고쳤다. 측정값은 [harness-spec.md](harness-spec.md) 변경 이력에 있다.

- DB 연결이 끊겨도 작업이 QUEUED로 남지 않고 FAILED로 보고한다 (`main.py`의 `_limited`, 연결 풀 `check_connection`).
- 추론 강도를 low로 낮추고(`LLM_REASONING_EFFORT`), 진단 최종 답을 10줄 이내로 제한했다.
- 진단 프롬프트에 실제 Loki 라벨을 알려 주고, 로그는 필터 없이 먼저 찾게 했다.
- 회복 확인은 20초 기다린 뒤 15초 rate 창으로 조회한다.
- 조치 제안은 도구 호출을 강제한다 (`tool_choice="required"`, 추론 강도 medium). 이 때문에 일반 질문에도 조치를 제안한다(7장).

### 2.2 진행 이벤트 확장

- 도구 이벤트(`TOOL_START`, `TOOL_END`)에 Node 이름을 싣는다.
- 회복 확인 대기(`STEP {node: verify, waitSeconds}`)와 보고서 작성 시작(`STEP {node: report}`)을 보낸다.
- backend가 TOKEN을 뺀 진행 이벤트를 모두 저장한다 (`task_events`, `V6__task_events.sql`). 조회: `GET /api/ai/tasks/{id}/events`.
- backend가 사람의 결정과 외부 반영 결과도 이벤트로 기록·중계한다: `APPROVAL_DECIDED {tool, decision, by}`, `CHANGE_FINISHED {result}`, `DONE`/`FAILED`.

### 2.3 작업 요약 분류

- 보고서를 쓰는 동안 같은 입력으로 에러 유형·원인·근거 조항을 분류한다 (`summary.py`, `prompts/summary.md`). 보고서 생성과 동시에 실행해 시간이 늘지 않는다.
- 에러 유형은 정해진 목록에서만 고른다: DB 커넥션 풀 고갈, 트래픽 급증, 파드 응답 불능, 외부 API 지연, 기타, 원인 미확정.
- 조치·승인·PR·회복·담당자 호출·공지는 모델이 아니라 State에서 그대로 옮긴다.
- 분류에 실패해도 보고서는 내보낸다(요약만 빠진다).
- 저장: `ai_tasks.summary` (JSONB, `V5__task_summary.sql`).

## 3. 승인

### 3.1 승인 카드 가독성

**문제:** 도구 이름과 인자 JSON이 그대로 보여서 무엇을 승인하는지 알기 어려웠다.

**변경:**
- 제목을 한글로 보여 준다 (예: "승인 필요: 담당자 호출", "런북 조치 실행").
- 인자를 도구별 항목 표로 보여 준다 (조치, 서비스, 레플리카 수, 호출 사유, 인시던트 번호, 공지 문안 등).
- 반영 방식(바로 실행 / 설정 저장소 PR)과 영향 한 줄을 붙인다.
- 근거 문서와 원본 인자는 접어서 둔다.
- 관리자 전용 도구(고객 공지, SLA 크레딧 확정)는 엔지니어에게 버튼 대신 "MSP 관리자만 승인·거절할 수 있다" 안내를 보여 준다. 기준은 backend `TaskService.ADMIN_ONLY_TOOLS`와 같다.

**코드:** `front/src/progress.js`(`toolLabel`, `approvalFields`, `approvalImpact`), `TaskView.vue`.

### 3.2 테스트용 자동 승인

**문제:** 테스트 중에 승인 요청을 하나씩 누를 수 없다.

**변경:**
- 관리자가 운영 개요의 설정 탭(10장)에 있는 "자동 승인 (테스트용)" 체크박스로 켜고 끈다. 켤 때 확인 창을 한 번 띄운다.
- 켜져 있으면 backend가 승인 요청(`APPROVAL_REQUIRED`)을 받는 즉시 승인하고 Agent를 재개한다. 조치, 담당자 호출, 고객 공지, 관리자 전용 도구 모두 해당한다.
- 켜져 있는 동안 MSP 직원 화면 상단에 경고 배너를 띄운다 (누가 켰는지 포함). 헤더에도 "자동 승인" 표시가 붙는다.
- 켜기 전부터 승인 대기 중이던 작업, GitOps PR 병합 대기(`CHANGE_PENDING`)에는 적용하지 않는다.
- 기록: 타임라인에 "자동 승인 (테스트 설정)", 감사 로그에 처리자 `auto-approve`, 설정 변경은 `AUTO_APPROVE_ON`/`AUTO_APPROVE_OFF`. `approvals` 테이블은 사람(users)만 기록하므로 자동 승인은 넣지 않는다.

| 항목 | 값 |
|---|---|
| 환경변수 | `AUTO_APPROVE_ALLOWED` (기본 `true`). `false`면 체크박스가 없고 API로도 켤 수 없다. **운영 환경에서는 `false`** |
| 저장 | `settings` 테이블 (`V7__settings.sql`). backend를 재시작해도 유지된다 |
| API | `GET /api/settings` (MSP 직원), `PUT /api/settings/auto-approve {enabled}` (관리자) |

**코드:** `settings/SettingsService.java`, `SettingsController.java`, `TaskService.java`, `front/src/settings.js`, `IncidentsView.vue`, `App.vue`.

**주의:** 조치 제안이 도구 호출을 강제하므로(2.1), 자동 승인을 켜 두면 일반 질문에서도 조치가 실행될 수 있다. 7장에서 막는다.

## 4. 작업 상세 화면

- **진행 타임라인:** 저장된 이벤트와 실시간 이벤트로 한글 타임라인을 그린다. 단계(컨텍스트 수집, 진단, 런북 검색, 승인, 조치, 반영, 회복 확인, 보고서), 경과 시간, 상태(진행 중 / 완료 / 대기 / 성공 / 실패)를 보여 준다. 끝난 작업도 과정을 다시 볼 수 있다.
- **상태 배지:** 승인·반영 이벤트가 오면 상단 상태가 새로고침 없이 바뀐다.
- **요약 표:** 에러 유형, 심각도·서비스, 원인, 근거 조항, 조치, 조치 승인, 반영·PR, 회복 여부, 에스컬레이션, 고객 공지.
- **보고서:** Markdown으로 렌더링한다. 모델 출력이므로 `DOMPurify`로 정리한 뒤 넣는다. 접을 수 있고, 요약 표가 있으면 접힌 채로 시작한다.
- **뒤로가기:** 상단에 "← 인시던트 목록" 링크.

**코드:** `TaskView.vue`, `front/src/progress.js`(`toTimeline`).

## 5. 운영 메인 화면

- **현황 카드:** 장애 수, 성공, 실패, 처리 중.
- **Agent 작업 결과 도넛:** 성공 / 실패 / 승인·반영 대기(`WAITING_APPROVAL`, `CHANGE_PENDING`) / 진행 중(`RUNNING`, `QUEUED`).
- **에러 유형 막대:** 요약(`summary.error_type`)이 있는 작업만 센다.

- **상태 배지:** 심각도, 인시던트 상태, 작업 결과를 색 배지로 보여 준다.
- **자동 승인 체크박스와 경고 배너:** 3.2.
- 화면 배치(사이드바, 헤더, 탭, 추이 차트)는 10장.

**코드:** `IncidentsView.vue`, `components/TaskStats.vue`, `components/StatusBadge.vue`.

## 6. 고객사 포털

**문제:** 기획안의 "고객사 담당자는 자기 회사 리포트를 본다"가 화면에 없었다. 고객사 담당자도 MSP 운영 화면(진단 과정, 런북, 승인 기록)을 그대로 봤다.

**변경:**
- `/portal`: 고객사 이름과 SLA(등급, 가용성 목표, 응답 기한), 처리 중·해결됨 수, 인시던트 목록. 30초마다 갱신.
- `/portal/incidents/{id}`: 발생·해결 시각, 처리 시간, 발송된 안내 공지, 장애 보고서.
- 보고서는 고객용 절(요약 / 조치와 결과 / SLA 영향)만 보여 준다. 진단 과정과 런북 같은 내부 정보는 뺀다.
- 공지 조회 API `GET /api/incidents/{id}/notices`: 감사 로그의 `NOTICE_SENT`를 읽는다. 다른 고객사 인시던트는 403.
- MSP 직원은 상단 "고객사 포털 미리보기"로 고객이 보는 화면을 볼 수 있다.

**코드:** `PortalView.vue`, `PortalIncidentView.vue`, `IncidentController.java`, `IncidentRepository.notices`, `Notice.java`.

## 7. 질문 처리: 인식된 장애가 없으면 "이상 없음"

**문제:** 조치 제안이 도구를 반드시 하나 고르게 돼 있어서(2.1), 인시던트가 없는 일반 질문에도 재시작이나 공지를 제안한다. 자동 승인을 켜 두면 질문만으로 조치가 실행된다.

**결정 (2026-10-19):** 일단은 인식된 장애가 없으면 진단·조치 없이 "이상 없음"이라고 답한다.

| 조건 | 동작 |
|---|---|
| 알림으로 생긴 작업 (`incident_id` 있음) | 지금과 같다 |
| 질문 작업이고, 그 고객사에 열린(`OPEN`) 인시던트가 없음 | 진단·런북 검색·조치 제안 없이 "현재 인식된 장애가 없다(이상 없음)"로 답하고 끝낸다 |
| 질문 작업이고, 그 고객사에 열린 인시던트가 있음 | **미정.** 우선 지금 동작을 유지한다 |

**구현:**
- agent `graph.py`
  - `load_context`: 질문 작업이면 그 고객사의 열린 인시던트 목록을 조회해 `context.open_incidents`에 둔다. 조회에 실패하면 `None`으로 두고 장애가 없다고 단정하지 않는다(지금 동작대로 진행).
  - `route_triage`: 인시던트 없는 작업이고 열린 인시던트가 0건이면 `no_issue` Node로 보낸다.
  - `no_issue`: 모델을 부르지 않고 "이상 없음" 답변을 보내고 끝낸다.
- MCP 어댑터는 빈 목록(`[]`)을 빈 내용으로 넘긴다. 빈 내용은 0건으로 읽는다.
- 요약 분류는 하지 않는다. 요약이 없으므로 메인 화면 에러 유형 차트에 섞이지 않는다.
- 승인 요청이 생기지 않으므로 자동 승인과 무관하다.
- 열린 인시던트가 있는 질문은 진단 컨텍스트에 `open_incidents`가 추가되는 것 외에는 지금과 같다.

**받아들인 한계:** 알림 기준에 못 미치는 문제(응답이 느리지만 임계치 아래 등)도 "이상 없음"으로 답한다. 이후 "인시던트 등록 필요"를 승인 요청으로 올리는 방식을 검토한다. 그때는 아래를 같이 처리해야 한다.
- Agent가 만든 인시던트에는 알림 fingerprint가 없어서, 같은 장애로 알림이 오면 인시던트가 중복 생성된다.
- Agent가 만든 인시던트는 알림 해제로 해결 처리되지 않는다.
- 인시던트 등록은 자동 승인에서 뺀다.

**확인 (2026-10-19):** 열린 인시던트가 없는 A사에 "order-api 지금 느린데 왜 그래?"를 물으면 도구 3개(고객사 정보, 서비스 구성, 인시던트 목록) 조회 후 약 2초 만에 "이상 없음"으로 끝난다. 승인 요청과 요약은 없다. 알림으로 시작하는 시나리오 A·B는 코드 경로가 바뀌지 않았고, 다시 돌려 확인하지는 않았다.

**테스트:** [T7](#t7-질문-처리-이상-없음).

## 8. 진단: 도구 없이 계획 글만 남기고 끝나는 문제

**문제:** 진단이 도구를 하나도 부르지 않고 조사 계획 글만 남기고 끝날 때가 있다. 이 글이 진단 결과(`findings`)가 되어 런북 검색어로 쓰이고, 근거 없이 조치 제안까지 간다.

**원인:**
- `prompts/diagnose.md` 1번이 "먼저 조사 계획을 3단계 이내로 적는다"고 지시한다. 모델이 첫 턴에 도구 없이 계획만 쓸 때가 있다.
- `_tool_loop`는 도구 호출이 없는 응답을 최종 답으로 보고 멈춘다.
- 계획 글은 `원인 미확정:`으로 시작하지 않으므로 `route_diagnose`가 런북 검색으로 보낸다.

**결정 (2026-10-19):** 첫 턴 도구 강제와 근거 없음 처리를 함께 적용한다.

| 변경 | 내용 |
|---|---|
| 첫 턴 도구 강제 | 진단 Node의 첫 턴만 `tool_choice="required"`로 부른다. 두 번째 턴부터는 지금처럼 모델이 정한다. 조치 제안(2.1)에서 이미 쓰는 방식이다 |
| 계획 받는 방식 | 프롬프트를 "첫 도구를 부르면서 같은 메시지에 조사 계획을 적는다"로 바꾼다. 도구를 강제하면 글이 비어 있을 수 있는데, 계획(`plan`)은 보고서 입력에 참고로만 쓰이므로 비어도 된다 |
| 근거 없음 처리 | 진단 Node에서 성공한 도구 호출(오류가 아닌 결과)이 하나도 없으면 진단 결과를 `원인 미확정: 도구로 근거를 모으지 못했다`로 바꾼다. 기존 분기가 런북 검색·조치 제안을 건너뛰고 보고서로 보낸다 |

**구현:**
- agent `graph.py`
  - `_tool_loop(force_first_tool=...)`: 첫 턴만 `tool_choice="required"` 모델로 부른다. 진단 Node만 켠다(회복 확인 Node는 지금과 같다).
  - `diagnose`: 성공한 도구 결과가 없으면 `findings`를 `원인 미확정: 도구로 근거를 모으지 못했다`로 바꾼다. Harness가 막은 호출(`ToolMessage.status == "error"`)은 성공으로 치지 않는다. MCP Server가 돌려준 오류 문자열은 성공으로 친다.
- `prompts/diagnose.md` 1번: "첫 도구를 부르면서 같은 메시지에 조사 계획을 적는다. 계획만 쓰고 도구 없이 끝내지 않는다."
- 환경변수 `DIAGNOSE_FORCE_FIRST_TOOL` (기본 `true`): 강제 없이 비교 평가할 때만 `false`로 둔다 (`config.py`, `harness.DIAGNOSE_FORCE_FIRST_TOOL`, `docker-compose.yml`, `.env.example`).

**영향:**
- 턴 수와 시간은 늘지 않는다. 계획만 쓰던 턴이 첫 도구 호출 턴이 된다.
- 회복 실패 후 다시 진단할 때도 첫 턴이 도구 호출이 된다. 재진단은 조치 이후 메트릭을 다시 봐야 하므로 맞는 동작이다.
- 질문 작업 중 열린 인시던트가 없는 경우는 7장에서 진단 전에 끝나므로 영향이 없다.

**다른 방법과 비교:**

| 방법 | 장점 | 단점 |
|---|---|---|
| 프롬프트만 수정 | 가장 간단하다 | 보장이 안 된다. 조치 제안도 프롬프트만으로는 5회 중 1회 실패했다 |
| 글만 오면 "도구를 호출하라"고 다시 요청 | 계획 글을 살린다 | 턴이 하나 늘어(5~10초) 120초 한도에 부담 |
| 계획 Node를 따로 두기 | 계획이 깔끔하게 남는다 | 모델 호출이 늘고 Graph 구조가 바뀐다 |
| **첫 턴 강제 + 근거 없음 처리 (채택)** | 턴 증가 없음, 근거 없는 조치를 구조적으로 막는다 | 계획 글이 가끔 비어 있을 수 있다 |

**확인 (2026-10-19):** diagnose Node만 단독으로 3회 실행했다(A사, 최근 2시간 안에 DB 커넥션 풀 장애 구간이 있고 측정 시점에는 회복된 상태, 9장 참고). 첫 턴 도구 호출 3/3, 원인 정답(HikariPool) 3/3, 2~4턴, 11~19초. 예상대로 계획 글(`plan`)은 3회 모두 비어 있었다. 결과는 [harness-spec.md](harness-spec.md) 변경 이력에 있다.

**남은 확인:** 시나리오 A·B를 각각 5회 끝까지 돌려 정답 원인(A: 커넥션 풀 고갈, B: 파드 응답 불능)과 120초 한도를 본다.

**테스트:** [T8](#t8-진단-첫-턴-도구-강제와-근거-없음-처리).

## 9. 진단: 과거 장애를 현재 장애처럼 보고하는 문제 (예정)

**문제:** 진단이 이미 끝난 장애를 지금 진행 중인 것처럼 보고한다.

**발견 경위 (2026-10-19 16:44):** 8장 확인 중 진단 결과가 "에러율 약 50%, HikariPool 타임아웃 반복"이었다. 그러나 그 시각 A사 order-api는 16:12에 회복된 뒤였다(에러 0건, 열린 인시던트 없음). 모델이 조회 범위를 `now-2h`로 잡아 15:28~16:12의 장애 구간을 근거로 썼고, 지금도 진행 중인지는 판단하지 않았다. 알림 파이프라인은 정상이었다. 같은 구간에 장애 3번이 모두 1분 안에 인시던트로 생성되고 회복 후 해결 처리됐다.

**원인:**
- `prompts/diagnose.md`는 "이상이 시작된 시각을 찾는다"만 지시한다. 지금도 이상인지 확인하라는 단계가 없다.
- 진단 결과 형식(`이상 시작 / 근거 / 직전 변경 / 추정 원인`)에 현재 상태 칸이 없다.
- 시각을 epoch 숫자(`1792392283`)로 써서 사람이 과거인지 알아보기 어렵다.

**영향:**
- 이미 회복된 장애에 조치를 제안한다. 알림이 짧게 울리고 저절로 회복된 경우, 회복 실패 후 다시 진단하는 경우에 생긴다.
- 보고서와 요약 표가 현재 상태를 잘못 전한다.

**결정 (안):** 현재 상태는 모델이 아니라 Harness가 잰다. 모델에게는 잰 값을 알려 주고 과거와 현재를 나눠 쓰게 한다.

| 변경 | 내용 |
|---|---|
| 현재 지표 측정 (코드) | 진단 시작 전에 Harness가 고정 쿼리 2개로 최근 1분 에러율과 p95 응답시간을 잰다. 모델 턴을 쓰지 않는다 |
| 현재 상태 판정 (코드) | 알림 규칙(`infra/prometheus/alert-rules.yml`)과 같은 기준을 쓴다. 에러율 20% 초과 또는 p95 1초 초과면 `진행 중`, 둘 다 아니면 `회복됨`, 측정 실패·요청 없음이면 `알 수 없음` |
| 진단 입력 | "현재 지표(Harness 측정): 에러율 x%, p95 y초, 상태: 회복됨" 을 진단 컨텍스트에 넣는다 |
| 진단 결과 형식 | 첫 줄에 `현재: 진행 중 / 회복됨 (에러율 x%, p95 y초)` 를 추가한다. 이상 구간은 `이상 구간: 시작 ~ 끝(또는 진행 중)` 으로 쓴다 |
| 시각 표기 | 프롬프트에 현재 시각(KST)을 주고, 시각은 `HH:MM (KST)` 로 쓰게 한다 |
| 조치 분기 (코드) | 측정 상태가 `회복됨`이면 런북 검색·조치 제안을 건너뛰고 보고서로 간다. 보고서에는 "조치 전에 회복됨"으로 남는다. 판정은 모델 글이 아니라 측정값으로 한다. `알 수 없음`이면 지금처럼 진행한다 |

**구현 위치 (예정):**
- agent `graph.py`
  - `diagnose` 시작 시 현재 지표 측정. 도구 호출 한도(Node마다 같은 도구 3회)를 진단과 나눠 쓰지 않도록 별도 Node 키(`measure`)로 부른다. `harness.NODE_TOOLS`에 `measure: {grafana_query_prometheus}`를 추가한다.
  - State에 `current: {error_rate, p95, status}` 추가.
  - `route_diagnose`: `current.status == "회복됨"`이면 `report`로 보낸다.
- `harness.py`: 판정 기준 상수(에러율 0.2, p95 1초). 알림 규칙과 값이 같아야 한다.
- `prompts/diagnose.md`: 현재 지표 사용, 결과 형식, 시각 표기.
- `prompts/report.md`: 현재 상태와 "조치 전에 회복됨" 경우의 문구.
- `front/src/progress.js`: `measure` 단계 이름("현재 지표 확인").

**구현 시 주의:**
- 에러가 0건이면 에러 시계열이 없어서 나눗셈 결과가 빈 값이 된다(16:46 Prometheus에서 확인). 분자에 `or vector(0)`을 붙인다.
- 서비스는 인시던트의 `service`로 거른다. 질문 작업이면 고객사 전체로 잰다. 고객사 구분은 `prom-label-proxy`가 강제하므로 쿼리에 tenant 라벨을 넣지 않는다.
- 측정 쿼리는 지금 데모 메트릭(`demo_orders_seconds`) 이름에 묶인다. 진단 프롬프트도 같은 이름을 쓰고 있어 새 의존은 아니다.

**다른 방법과 비교:**

| 방법 | 장점 | 단점 |
|---|---|---|
| 프롬프트만 수정 ("현재 값도 확인하라") | 간단하다 | 확인 여부와 판정이 모델에 달려 있다. 8장처럼 가끔 빠진다 |
| 결과 형식에 `현재:` 줄을 넣고 그 글로 분기 | 코드가 적다 | 모델이 쓴 글을 파싱한다. 형식이 어긋나면 분기가 틀린다 |
| **Harness 측정 + 측정값으로 분기 (안)** | 판정이 항상 같다. 모델 턴을 쓰지 않는다 | 고정 쿼리와 기준값을 알림 규칙과 맞춰 관리해야 한다 |

**확인할 것:**
- 회복된 상태(지금)에서 A사 장애 작업을 진단하면 `회복됨`으로 판정되고 조치 제안 없이 보고서로 끝나는지.
- 시나리오 A 진행 중에 진단하면 `진행 중`으로 판정되고 지금처럼 조치까지 가는지.
- 에러 0건일 때 에러율이 빈 값이 아니라 0%로 나오는지.

## 10. 화면 디자인: 사이드바·헤더·탭 레이아웃

**문제:** 상단 링크 몇 개와 카드만 세로로 쌓인 화면이라 운영 콘솔처럼 보이지 않았다. 어느 화면에 있는지, 지금 처리 중인 장애가 있는지 한눈에 보이지 않았고, 시간 표기도 화면마다 달랐다(`9시 22분 44초`, `2026. 10. 19. 오후 5:48:57`).

**변경:** 산업용 모니터링 콘솔(Vaisala viewLinc)의 배치를 참고해 틀을 바꾼다. 기능과 API는 그대로다.
- **왼쪽 사이드바:** 남색 바탕에 로고와 메뉴. 선택된 메뉴는 민트색으로 표시한다. 아래 버튼으로 아이콘만 남게 접고, 접은 상태는 브라우저에 기억한다. 화면 폭이 960px보다 좁으면 항상 접는다.
  - MSP 직원: 운영 개요, 고객사 포털 미리보기
  - 고객사 담당자: 장애 현황
- **상단 헤더:** 왼쪽에 화면 제목(운영 개요, 작업 상세, 장애 현황, 인시던트 상세), 오른쪽에 자동 승인 표시, 처리 중인 인시던트 수(종 아이콘, 30초마다 갱신), 사용자·역할, 로그아웃, 시계. 종 아이콘을 누르면 인시던트 목록으로 간다.
- **운영 개요 탭:** 헤더 아래 탭으로 나눈다. 탭은 주소(`?tab=`)에 남아 새로고침해도 유지된다.
  - **대시보드:** 기존 운영 메인 화면 순서를 그대로 둔다. 현황 카드 → 작업 결과·에러 유형 → Agent에게 묻기 → 인시던트 목록. 그 아래에 추이 차트를 붙인다.
  - **Agent 작업:** 작업 전체 목록(시작, 고객사, 종류, 내용, 상태). 진행 중인 작업 수를 탭 이름에 붙인다.
  - **설정:** 자동 승인 체크박스(3.2). 관리자이고 `AUTO_APPROVE_ALLOWED=true`일 때만 보인다.
- **현황 카드:** 처리 중인 장애(전체 건수 함께), 작업 성공, 작업 실패, 처리 중인 작업(승인·반영 대기 건수 함께)을 색 띠가 있는 카드 4장으로 나눈다.
- **인시던트 목록:** 처리 중 / 해결됨 / 전체로 거른다. 고객사는 ID 대신 이름으로 보여 준다.
- **추이 차트:** 시간 구간별 인시던트 발생, Agent 작업, 실패한 작업 건수를 선으로 그린다. 따로 API를 부르지 않고 이미 받은 목록으로 센다.
  - 기간: 6시간(30분 단위), 24시간(1시간 단위), 7일(6시간 단위). 구간 경계는 현지 시각 정각에 맞춘다.
  - 화살표로 이전·다음 구간으로 넘긴다.
  - 아래 표에서 선마다 표시를 켜고 끄고, 합계·구간 최대·마지막 구간 값을 보여 준다.
- **시간 표기 통일:** 날짜와 시각은 `10/19 17:48`, 갱신 시각은 `09:23:22`로 쓴다 (`format.js`).

## 11. 조치 판단: 공통 런북·서비스 카탈로그·HPA

설계와 결정은 [SPEC-fault-based-actions](specs/SPEC-fault-based-actions.md)와 [ADR 0001](adr/0001-tenant-infra-actions-hybrid-environment.md) D7~D9에 있다.

**바꾼 것**

- 공통 런북 RB-STD-01~07. 고객사 문서는 계약과 서비스별 절차만 남겼다.
- 서비스 카탈로그(V8)와 backend 계산값(안전 상한, 무중단 재시작, 할 수 있는 조치). backend가 조치 요청을 같은 값으로 다시 검사한다.
- A사 HPA(최소 2, 최대 3)와 `adjust_autoscaler`(V10). HPA 대상의 직접 확장은 거부한다.
- 에스컬레이션 발송 대기열(V9). 분류별로 받는 사람과 메시지를 정한다. 실제 발송은 없다.

- Agent: 진단 시작 때 코드가 지표·로그 신호·최근 변경을 먼저 조회한다. 조치 제안은 조항과 맞지 않거나 할 수 없는 조치를 최대 두 번 돌려보낸다. 회복 확인은 두 번 재서 둘 다 기준 안이어야 회복이다.

## 12. 작업 전달: Kafka 기본화와 확장성

설계는 [SPEC-kafka-scale](specs/SPEC-kafka-scale.md), 결정은 [ADR 0002](adr/0002-kafka-default-task-delivery.md)에 있다.

**문제:** 발행 결과를 확인하지 않아 브로커가 잠깐 멈추면 작업이 QUEUED로 남았다. 한 묶음을 동시에 돌리고 묶음이 끝나야 커밋해서, 같은 고객사 순서가 깨지고 재시도 대기가 새 작업을 막았다. 리밸런싱으로 다시 받은 미완료 작업을 버렸다.

**바꾼 것**

- Transactional Outbox(V12 `task_outbox`)와 Relay. 5번 실패하면 작업 FAILED.
- 등급별 소비자 그룹, 파티션 단위 순서, 레코드 단위 커밋, 재시도 토픽 등급별 분리(`retry_after_ms`), 실행 슬롯 공유와 Gold 우선.
- 실행 임대(`task_budget.owner`, `heartbeat_at`)와 끊긴 작업 주기 점검.
- `agent-migrate`(Alembic) 컨테이너. agent는 기동 때 DDL을 하지 않는다.
- Kafka가 compose 기본이고 healthcheck를 둔다. `cluster-up.sh`는 HPA 첫 지표와 ArgoCD 동기화까지 기다린다.

**결과:** 브로커 20초 중단 → 4번째 시도에 발행, 작업 DONE. 계속 중단 → 약 58초 뒤 FAILED. 실행 파드 강제 종료 → 89초 뒤 다른 파드가 이어 감, 중복 승인 요청 없음(SPEC-kafka-scale 14장).

## 13. 고객 공지: 문안 규칙 검사

## 14. 조치 판단: Jev 장애 형태 판정 (진행 중)

**문제:** 장애 형태(공통 런북 조항)는 조치 제안 모델이 프롬프트를 읽고 고른다. `_signal_clause`는 RB-STD-01~03이 신호로 하나만 맞을 때만 정하고, 나머지(04, 05, 07, 신호가 섞인 경우)는 모델에 맡긴다. 모델 호출 한 번이 108초 걸려 작업 시간 한도(120초)에 걸린 적이 있다(시나리오 B 첫 실행).

**바꿀 것:** [TypeSafe](https://typesafe.ai)의 Jev(System One, 선택지 하나를 확률과 함께 고르는 판정 모델)로 조항을 고른다.

- 입력: 코드가 진단 시작 때 조회한 `signals`(지표, 로그 신호 건수, 직전 변경). Jev는 숫자 비교에 약해서 코드가 기준과 비교해 글로 바꿔 넘긴다. 에러율은 5%(`_signal_clause`와 같은 기준), p95는 1초(`P95_THRESHOLD_SECONDS`)와 비교한다.
- 질문: 선택지 하나. RB-STD-01·02·03·04·05·07. RB-STD-06은 장애 형태가 아니라 조치를 할 수 있는지에 관한 조항이라 뺀다.
- 1단계(이번): `agent/jev.py`와 테스트만 둔다. `graph.py`는 고치지 않는다. 실제 키로 알려진 장애 형태를 넣어 맞히는지 본다.
- 2단계(1단계 결과를 보고 정함): 조치 제안 때 판정을 작업 이벤트로만 남겨 모델이 고른 조항과 비교한다. 3단계에서 확신도가 높을 때 조항을 고정하고 `_clause_mismatch`로 맞지 않는 조치를 돌려보낸다.
- Jev 호출이 실패하거나 늦으면(5초) 판정 없음(`None`)으로 두고 지금 동작을 그대로 쓴다. 키(`TYPESAFE_API_KEY`)가 없으면 호출하지 않는다.
- `typesafe-sdk`는 2단계 전까지 `pyproject.toml`에 넣지 않고 `uv run --with typesafe-sdk`로 실행한다.

### T14. 조치 판단: Jev 장애 형태 판정

**검증할 것:** 지표 숫자를 기준과 비교한 글로 바꿔 Jev에 넘기고, Jev 답을 조항·확신도·확률로 돌려준다. Jev가 실패하거나 늦거나 키가 없으면 예외 없이 판정 없음이다.

**단위 테스트:** `server/python/agent/tests/test_jev.py`. Jev 호출은 가짜 클라이언트(`system_one`이 `AsyncMock`)로 바꾼다. 키와 네트워크가 없어도, `typesafe-sdk`가 설치되지 않아도 돈다.

**실측(자동 테스트 아님):** `scripts/jev_probe.py`가 `.env`의 키로 알려진 장애 형태 7가지를 넣고 Jev 판정, 확신도, `_signal_clause` 판정을 기대 조항과 나란히 출력한다. A사 커넥션 풀(01), B사 멈춤(02), 트래픽 급증(03), 외부 지연(04), DB 지연(05), 로그 신호 없는 5xx(07), 커넥션 풀 고갈과 DB 지연이 섞임(05).

**실행:**

```bash

uv run --with typesafe-sdk python scripts/jev_probe.py
```

**결과 (2026-10-20):**
- 단위: `test_jev.py` 2건 통과. agent 테스트 전체 55건 통과. `typesafe-sdk` 없이 돈다.
- 실측(`--repeat 3`, `jev-1.13.0`): 7가지 × 3번 = 21번 모두 기대 조항. 같은 입력의 판정은 3번 모두 같았다. 확신도는 DB 지연만 0.99(2순위 RB-STD-07 0.01)이고 나머지는 1.00. 호출 한 번 0.2~0.4초.
- 코드 규칙과 다른 경우: 커넥션 풀 고갈과 DB 지연이 섞이면 `_signal_clause`는 RB-STD-01, Jev는 RB-STD-05. 런북 RB-STD-01의 구분("DB 자체 지연 로그는 없다")과 구조 검토("DB가 지연·장애 상태면 RB-STD-05")로는 RB-STD-05가 맞다. `_signal_clause`의 RB-STD-01 조건에 `slow_query`가 없는지 보는 부분이 없다. 팀원과 확인한 뒤 고친다.
- 한계: 입력이 선택지 설명과 거의 그대로 맞는 쉬운 경우라 확신도 1.00이 많다. 섞인 경우의 답도 선택지 설명("커넥션 풀 고갈 로그가 같이 있어도 DB 지연이 있으면 이 조항")에 적어 둔 것이다. 확신도가 실제 정답률과 맞는지는 2단계에서 실제 작업의 판정을 모아 본다.

## 자동 회고 축적과 다음 진단 연결 (2026-10-22)

종료된 장애의 완료 보고서를 backend의 고객사별 `/internal/tenants/{tenantId}/postmortems` API로
100건씩 읽어 `docs.chunks`에 색인한다. 새 기본 서비스 `postmortem-indexer`가 매 순회 후 60초를 기다려
다시 전체 이력을 확인하므로 기존 장애와 늦게 도착한 보고서도 반영한다. app DB 직접 접근은 추가하지 않는다.
내용·모델이 같은 문서는 임베딩을 건너뛰고, 변경된 문서는 트랜잭션으로 교체한다.

Agent는 첫 진단에서 같은 고객사의 회고를 검색해 현재 근거와 비교하고, 작업 근거 목록에 출처를 남긴다.
자동 회고는 미검토 기록으로 표시한다. 현재 장애 자체와 다른 고객사 사례는 제외하며, 회고 검색 실패는
현재 메트릭·로그 진단을 막지 않는다. 고객사별 조치 승인과 계약·구조 검사는 그대로 적용한다.

운영·테스트 명령은 README의 문서 색인 절과 `docs/testing.md`에 있다. 새 의존성이나 업무 DB 마이그레이션은 없다.


## Slack 연결 설정과 발송 검토 (2026-10-22)

관리자가 고객사별 Incoming Webhook URL과 채널 이름을 화면에서 저장할 수 있다.
연결 전에도 장애 대응은 동작하며 연결 저장만으로 과거 메시지가 발송되지 않는다.
작업 상세에서 기존 에스컬레이션의 문안을 수정·검토하고 사용자가 Slack 발송을 승인하면
별도 outbox에 저장한다. Agent의 테스트 자동 승인은 이 사용자 API를 호출하지 않는다.

Webhook은 AES-GCM으로 암호화하며 API 응답에는 저장 여부·사용 여부·채널 이름·버전만 포함한다.
설정 버전이 바뀌면 이전 미리보기 승인을 거부하고 대기 발송을 취소한다. 동시 승인/워커의 중복 처리를
DB에서 막고, 429만 자동 재시도하며 전송 결과가 불명확하면 수신 여부 확인 상태로 남긴다.
발송은 별도 실행 스레드에서 수행해 기존 작업 전달·GitOps 점검 스케줄을 막지 않는다.

V13 마이그레이션(`slack_connections`, `slack_deliveries`)이 추가됐다.
내부 운영 채널 알림을 지원하며 고객 공지 외부 발송·이메일·개인 DM은 이번 범위에 없다.
설정·발송 절차와 검증은 README 및 testing.md를 참조한다.
