# Spec: 겹친 장애의 원인 순위

- 상태: **구현 완료, 검증 전** (2026-10-23). 결정 4개를 모두 추천안으로 정했다 (9장). 테스트는 작업을 모두 끝낸 뒤 한 번에 돌린다
- 근거: [SPEC-fault-based-actions](SPEC-fault-based-actions.md)(장애 × 고객사 매트릭스), [SPEC-limitations-fixes](SPEC-limitations-fixes.md) 4단계(서비스별 관측), `prompts/diagnose.md`, `prompts/propose.md`, `agent/action_guards.py`
- 흐름 전체: [장애 처리 흐름](../장애-처리-흐름.md)
- 원칙: 지금 시스템의 원칙(`signals.py`: 코드는 조회하고 판단하지 않는다)을 지킨다. **코드는 사실을 조회해 후보별로 정리하고, 원인 후보와 순위는 에이전트가 판단하며, 코드는 명백한 위반만 막는다.** 순위가 판단 기준과 달라도 막지 않고 기록하며, 맞는지는 E2E가 판정한다. 단계마다 테스트를 붙이고 따로 커밋한다.

## 1. 목표

한 서비스에 원인이 둘 이상 겹쳐도

1. 코드가 원인 후보별 사실(신호 건수, 처음 나온 시각, 의존 대상 상태와 비율, 직전 변경)을 정리해 넘긴다
2. 에이전트가 원인 후보를 모두 적고, 판단 기준에 따라 순위와 흡수 관계를 정하고 근거를 쓴다
3. 에이전트가 1순위 원인의 조치를 고르고, 코드가 명백한 위반만 막는다
4. 회복되지 않았으면 처리한 원인의 신호를 코드가 조치 뒤 구간으로 다시 세어 넘긴다. 에이전트는 사라졌으면 다음 원인을, 그대로면 같은 원인의 에스컬레이션을 고른다. 같은 원인에 앱 조치를 또 하는 것은 코드가 막는다
5. 보고서에 원인 후보 순위와 각 근거, 처리한 순서를 남긴다

**완료 기준:** 단위 테스트(사실 표, 후보 파싱, 검사 ①②③, 회복 확인 뒤 분기), 지금 E2E 15개가 그대로 통과(원인 하나일 때 동작이 바뀌지 않는다), 새 복합 장애 E2E 3개 통과.

## 2. 지금

흐름 전체는 [장애 처리 흐름](../장애-처리-흐름.md) 1장에 있다. 겹친 장애에서 문제가 되는 곳:

| 위치 | 하는 일 | 겹친 장애에서의 문제 |
|---|---|---|
| `diagnose.md` 6~7단계 | "가능성 높은 원인 1~3개"를 고르고 장애 형태 표에서 행 하나를 고른다 | 표가 로그 신호의 **있음/없음**만 본다. 두 행이 맞을 때 고르는 기준이 없다. 명시된 우선순위는 "`slow_query`가 있으면 풀 고갈보다 RB-STD-05" 하나 |
| `propose.md` 1단계 | 같은 표로 장애 형태 하나를 정한다 | 같음 |
| `action_guards.signal_clause` | 코드가 RB-STD-01~03 중 하나로 정해 ACTION_BLOCKED 검사에 쓴다 | 둘 이상 맞으면 `None`(검사 포기) |
| `jev.classify_fault` | 조항 하나와 확신도 | 나머지 후보가 기록되지 않는다 |
| `route_verify` | 미회복이면 한 번 다시 진단(`attempts < 1`) | 처리한 원인을 빼지 않고 처음부터 판단한다. 같은 원인에 다른 조치를 시도할 수 있다 |
| `route_execute` | 고객 공지·에스컬레이션은 회복 확인 없이 보고서로 간다 | (문제 아님) 복합 장애에서 공지·에스컬레이션이 마지막 조치가 된다 |
| backend 알림 웹훅 | 알림 지문(fingerprint)마다 인시던트·작업 하나 | 같은 서비스에 `HighErrorRate`와 `HighLatency`가 함께 울리면 **인시던트 두 개, 작업 두 개가 같은 서비스를 동시에 진단·조치**한다 |
| 데모 앱 `FaultState` | 장애 하나(`AtomicReference<Fault>`) | 겹친 장애를 만들 수 없다. 상태가 파드 메모리라 재시작하면 외부·DB 장애까지 사라진다 |

## 3. 원인 후보별 사실 (코드, 판단하지 않는다)

`signals.cause_facts(signals, dependencies, recent_change, incident) -> list[CauseFacts]`를 새로 둔다. 코드가 조회한 값을 조항별로 모을 뿐 순위나 흡수는 정하지 않는다.

구현은 `signals.py`의 다른 값처럼 사전(dict)이다. 필드는 아래와 같다.

```python
class CauseFacts:   # 사전의 키
    clause: str                 # RB-STD-01..05
    signal_count: int           # 그 조항의 로그 신호 건수
    first_seen: str | None      # 그 신호가 처음 나온 시각
    dependency: str | None      # RB-STD-04·05: 의존 대상 이름
    dependency_status: str | None    # HEALTHY | DEGRADED | DOWN | UNKNOWN
    dependency_share: float | None   # 의존 대상 p95 / 요청 p95
    evidence: bool              # 3.1의 근거 조건을 채웠나 (검사 ①의 기준)
```

### 3.1 근거가 있다고 보는 조건 (`evidence`)

이 조건은 순위가 아니라 **"근거 없는 원인"을 가려내는 최소 기준**이다. 검사 ①(4.2)에만 쓴다.

| 조항 | 근거 조건 (하나라도) |
|---|---|
| RB-STD-01 풀 고갈 | `connection_pool_exhausted` ≥ 3건 |
| RB-STD-02 작업 스레드 고갈 | `worker_pool_saturated` ≥ 3건 |
| RB-STD-03 트래픽 급증 | `request_queue_backlog` ≥ 3건 |
| RB-STD-04 외부 의존 지연 | `external_api_timeout` ≥ 3건, 또는 외부 의존 대상 DEGRADED·DOWN |
| RB-STD-05 DB 자체 지연 | `slow_query` ≥ 3건, 또는 DB 의존 대상 DEGRADED·DOWN |

- 3건 미만은 잡음으로 본다(`MIN_SIGNAL_COUNT = 3`).
- 의존 대상 상태는 지금 에이전트가 `business_get_dependency_health`로 직접 본다. 진단 시작 때 서비스의 `dependencies`마다 **코드가 미리 조회**한다(직전 변경 조회와 같은 방식). 에이전트는 더 볼 필요가 있을 때만 직접 부른다.
- **신호 건수와 `first_seen`은 신호마다 Loki 집계로 구한다** (`signals.log_signal_details`). `sum(count_over_time({…} |= "<문구>" [5s]))`를 5초 간격 range로 조회해, 구간 합을 건수로, 처음 0이 아닌 구간의 시작을 `first_seen`으로 쓴다. 지금 반복 메시지 요약은 최신 200줄만 보는데, 파드 멈춤처럼 초당 수십 줄 나오는 신호가 있으면 200줄이 몇 초 분량이라 함께 난 다른 신호가 0건으로 세지고 처음 시각도 알 수 없기 때문이다(1단계에서 mcp-grafana로 확인). 조회에 실패한 신호는 요약으로 센 값을 남긴다. `signals.logs`(조치 검사와 Jev의 입력)도 이 값으로 바꾼다.
- 에러율·p95는 지금처럼 따로 준다. 조항별 지표 조건(예: RB-STD-02는 에러율 ≥ 0.05)은 판단 기준(3.2)에서 에이전트가 본다.

### 3.2 판단 기준 (에이전트, `diagnose.md`)

`diagnose.md` 6~7단계의 판정표를 아래 기준으로 바꾼다. 코드가 강제하지 않는다.

**흡수:** 아래 계층의 원인이 위 계층의 증상을 설명하면, 위 계층 후보는 독립 원인이 아니라 증상으로 적는다.

| 증상으로 볼 후보 | 원인 후보 | 조건 | 이유 |
|---|---|---|---|
| RB-STD-01 풀 고갈 | RB-STD-05 DB 지연 | 직전 설정 변경이 **없을 때** | 느린 쿼리가 커넥션을 오래 잡는다 (지금 판정표의 규칙과 같다) |
| RB-STD-03 트래픽 급증 | RB-STD-04, 05 | 그 의존 대상 비율(`dependency_share`)이 0.5 이상 | 의존 호출이 처리 시간을 차지한다 |
| RB-STD-03 트래픽 급증 | RB-STD-02 | 항상 | 묶인 작업 스레드가 대기열을 만든다 |

**직전 설정 변경이 있으면 풀 고갈은 증상으로 보지 않는다.** 풀 크기를 줄인 배포와 DB 지연이 같이 있으면 두 원인 모두 진짜다. 지금 규칙(DB 지연이면 RB-STD-05)대로라면 DBA 에스컬레이션만 하고 롤백은 하지 않아 5xx가 남는다.

**순위:** 흡수하고 남은 독립 원인의 처리 순서.

1. 근거가 지표와도 맞는 원인 > 로그 신호만 있는 원인 > 의존 대상 상태만 있는 원인
2. **바로 고칠 수 있는 앱 원인 먼저** (결정 9.1): RB-STD-01·02·03(앱 조치) > RB-STD-05(DBA 에스컬레이션) > RB-STD-04(고객 공지). 앱 원인을 먼저 고치면 남은 증상이 외부·DB 원인 하나로 좁혀진다. 외부·DB 후보는 처음부터 보고서와 진행 화면에 보이므로 사람이 기다리지 않아도 된다. 앱 조치가 계약상 불가해도 순위는 그대로이고, 조치는 그 조치의 승인 요청(`ACTION_BLOCKED`)이 된다.
3. 먼저 시작한 쪽 (`first_seen`)
4. 신호 건수가 많은 쪽

2번은 "가능성"이 아니라 "처리 순서"다. 기준과 다르게 정하려면 그 근거를 적는다.

**출력 형식:** 지금 형식의 `추정 원인`과 `장애 형태` 줄을 아래로 바꾼다. 코드가 이 줄을 읽어 검사와 보고서에 쓴다.

```
원인 후보:
1) RB-STD-02 작업 스레드 고갈 — worker_pool_saturated 412건, 에러율 0.93 (흡수: RB-STD-03)
2) RB-STD-04 외부 의존 지연 — payment-gateway DEGRADED, 비율 0.71
처리할 원인: RB-STD-02
병목: 앱
```

후보가 없으면 지금처럼 `원인 미확정:`으로 시작한다. 후보가 하나면 지금과 같은 결과가 나와야 한다. E2E 15개가 그대로 통과하는 것이 그 확인이다.

## 4. Agent 흐름

### 4.1 진단

- `diagnose`가 `cause_facts`를 부르고, 그 표를 요청에 넣는다(지금의 "알려진 로그 신호 건수" 자리).
- 에이전트가 3.2 기준으로 원인 후보, 순위, 처리할 원인을 쓴다.
- 코드가 출력의 `원인 후보`와 `처리할 원인` 줄을 읽어 `state["causes"]`(조항 순서 목록)와 `state["target_clause"]`에 둔다. 형식이 깨져 읽지 못하면 지금처럼 검사 없이 진행하고 기록만 남긴다.
- 조치 뒤 다시 진단할 때는 처리한 원인(`state["handled"]`)과 그 신호의 지금 건수를 함께 준다.

### 4.2 조치 제안과 검사

- `propose.md` 1단계: 판정표 대신 "진단이 정한 처리할 원인"을 따른다고 적는다. 장애 형태를 다시 고르지 않는다.
- `action_guards.first_problem`에 검사 셋을 더한다. 기존 검사처럼 거부 이유를 돌려주고 다시 고르게 한다(최대 2번).

| 검사 | 거부하는 경우 | 이유 |
|---|---|---|
| ① 근거 없는 원인 | `target_clause`의 `evidence`가 false | 신호가 없는 원인에 조치하지 않는다 |
| ② 같은 원인 반복 | `target_clause`가 이미 `handled`에 있는데 **앱 조치**를 고름 | 효과가 없던 원인에 다른 앱 조치를 시도하지 않는다. 같은 원인의 에스컬레이션은 된다(최대치를 올려도 회복되지 않은 트래픽 급증의 `ACTION_BLOCKED`, a-surge-max) |
| ③ 조항 불일치 | 제안한 조치가 `target_clause`를 고치는 조치(`action_guards.fixes`)가 아니고, 그 조항의 에스컬레이션·공지도 아님 | 진단과 다른 원인을 조치하지 않는다 |

- 순위 자체(1순위로 무엇을 골랐는지)는 막지 않는다. 원인 후보, 처리할 원인, 사실 표를 작업 이벤트(STEP)에 기록하고, 3.2 기준대로였는지는 E2E가 판정한다.
- `signal_clause`는 `target_clause`가 있으면 그것을 쓴다. 그래서 ACTION_BLOCKED 검사가 신호가 둘 이상인 경우에도 동작한다.
- Jev 판정은 지금처럼 받는다. `target_clause`와 다르면 기록만 하고 에이전트에 전달하지 않는다.

### 4.3 회복 확인 뒤

앱 조치를 실행하면(`EXECUTED`, `PR_CREATED`) `state["handled"]`에 `{clause, action, signal, signal_count_before, at}`를 쌓는다. 회복되지 않으면 verify가 그 신호를 조치 뒤 구간으로 다시 세어 `signal_count_after`와 `cleared`(조치 전의 20% 미만)를 더한다. 어디로 갈지는 지금처럼 코드가 정하고, 다음 원인은 에이전트가 고른다.

| 조치 뒤 | 다음 |
|---|---|
| 지표 회복 | 보고서 |
| 미회복, 다시 진단한 적 없음 | 다시 진단. 처리한 원인과 다시 센 신호를 함께 준다. 신호가 사라졌으면 에이전트가 다음 원인을, 남아 있으면 같은 원인의 에스컬레이션을 고른다. 같은 원인에 앱 조치를 또 하면 검사 ②가 돌려보낸다 |
| 미회복, 다시 진단 횟수 한도 도달 | `NOT_RECOVERED` 에스컬레이션 (처리하지 못한 원인 후보를 사유에 적는다) |
| 고객 공지·에스컬레이션을 실행함 | 지금처럼 회복 확인 없이 보고서 (`route_execute`) |

같은 원인의 신호가 그대로일 때 코드가 바로 최종 에스컬레이션으로 보내지 않는 이유: 최대치를 올려도 회복되지 않은 트래픽 급증은 "구조상 더 늘릴 수 없다"는 `ACTION_BLOCKED` 에스컬레이션이 정상 흐름이다(a-surge-max). 바로 `NOT_RECOVERED`로 보내면 받는 사람과 분류가 바뀌어 지금 E2E가 깨진다.

다시 진단 횟수 한도는 지금처럼 1번이다(조치 최대 2개). 결정 9.2.

### 4.4 보고서

- 보고서에 "원인 후보" 절을 둔다: 순위, 조항, 근거, 증상으로 본 후보, 처리 여부. 3.2 기준과 다른 순위였으면 에이전트가 적은 근거도 싣는다.
- `summary.py`의 `cause`(한 문장)는 그대로 두고 `other_causes: list[str]`를 더한다. 화면 요약 표는 처리한 원인만 보여 주고, 나머지는 보고서에서 본다(범위 밖 10장).

## 5. 같은 서비스의 인시던트 묶기 (backend)

**지금:** 알림 지문마다 인시던트를 연다. 같은 서비스에 다른 알림이 울리면 작업 두 개가 같은 서비스를 동시에 조치한다.

**바꿀 것:** 같은 `(tenant, service)`에 열린 인시던트가 있으면 새 인시던트를 열지 않는다. 알림이 모두 해제돼 닫혔어도 그 인시던트의 진단 작업이 아직 진행 중이면 다시 열고 덧붙인다. 파드 멈춤을 재시작으로 고친 직후 에러율 알림이 풀리고, 가려져 있던 결제 지연 알림이 울리는 경우다. 작업 하나가 두 원인을 이어서 처리해야 한다. 두 알림이 동시에 와도 인시던트가 둘 생기지 않게 (고객사, 서비스)마다 잠근다(`pg_advisory_xact_lock`). 서비스 라벨이 없는 알림은 묶을 기준이 없어 지금처럼 알림마다 연다.

- 기존 인시던트에 알림을 덧붙인다(`incident_alerts` 테이블: incident_id, fingerprint, alertname, started_at, resolved_at).
- 심각도가 더 높으면 올린다(warning → critical).
- 인시던트는 묶인 알림이 **모두** 해제될 때 닫는다.
- 진행 중인 작업에 "알림 추가" 이벤트를 남긴다. 작업을 새로 만들지 않는다. 진행 중인 작업은 다음 진단(조치 뒤 다시 진단)에서 새 신호를 함께 본다.

결정 9.3.

## 6. 데모 앱과 장애 주입

### 6.1 장애를 겹쳐 넣는다

- `FaultState`를 `Set<Fault>`로 바꾼다. 관리 API에 추가와 해제를 따로 둔다(`POST /admin/faults/{fault}`, `DELETE /admin/faults/{fault}`, 기존 단일 주입 API는 "모두 해제 후 하나 추가"로 유지).
- 요청 처리에서 장애가 겹치는 모양은 지금 코드 순서를 따른다. 파드 멈춤(`WORKER_HANG`)은 의존 호출 전에 요청을 거부하므로 외부·DB 지연을 **가린다**. 재시작한 뒤에야 외부 지연이 보인다. 실제 장애에서도 흔한 모양이고, 4.3의 "처리한 원인의 신호가 사라지면 다음 순위"가 이것을 다룬다.
- `scripts/inject.py`: `inject.sh tenant-a hang+latency`처럼 `+`로 여러 종류를 받는다. 관리 API 주입은 더하기(`POST /admin/faults/{fault}`)로 바꿔, 잘못된 배포의 풀 고갈 위에 다른 장애를 얹을 수 있다. 겹쳐 넣을 때는 의존 장애 ConfigMap을 먼저 쓴다. 잘못된 배포(pool)가 띄우는 새 파드가 그 값을 이어받게 하기 위해서다.

### 6.2 외부·DB 장애는 재시작해도 남는다

**지금:** 장애 상태가 파드 메모리라 `restart_pods`가 결제 지연과 DB 지연까지 없앤다. 외부 API가 느린데 앱 재시작으로 회복되는 것은 사실과 다르고, 복합 장애에서 첫 조치(재시작)가 모든 원인을 지워 버린다.

**바꿀 것:** 앱 내부 장애(`WORKER_HANG`, `DB_POOL_EXHAUSTION`)는 지금처럼 메모리에 둔다. 의존 대상 장애(`PAYMENT_LATENCY`, `DB_SLOW`)는 파드 밖에 둔다.

- 고객사 네임스페이스에 ConfigMap `dependency-faults`를 두고 볼륨으로 마운트한다(`optional: true`, 없으면 장애 없음). 데모 앱은 **시작할 때만** 파일을 읽는다. 계속 읽으면 관리 API로 해제한 장애가 갱신 전의 파일 때문에 되살아난다.
- `inject.py`는 ConfigMap을 고치고, 동시에 떠 있는 파드의 관리 API에도 바로 넣는다. kubelet이 ConfigMap 볼륨을 갱신하기까지 최대 1분쯤 걸리므로 즉시 반영은 관리 API로 하고, ConfigMap은 새 파드가 시작할 때 읽는 용도다.
- 환경변수가 아니라 볼륨인 이유: 환경변수를 바꾸면 배포가 바뀌어 "직전 설정 변경"으로 잡히고 RB-STD-01 판단을 흐린다.
- A사 ConfigMap은 GitOps 저장소가 아니라 E2E와 `inject.py`가 직접 만든다(ArgoCD가 관리하지 않게 `kustomization.yaml`에 넣지 않는다).

## 7. E2E

### 7.1 복합 장애 시나리오

| 키 | 고객사 | 주입 | 기대 |
|---|---|---|---|
| `a-hang-latency` (지금 `b-hang-latency`, B사 `checkin-api`. SPEC-e2e-speed ③) | A사 | 파드 멈춤 + 외부 결제 지연 | 처리할 원인 RB-STD-02 → 재시작 → 미회복(결제 지연이 드러남), 재시작한 원인의 신호는 사라짐 → 다시 진단 → RB-STD-04 고객 공지 → 보고서(공지는 회복 확인을 하지 않는다). 조치 순서 `restart_pods` → `business_send_customer_notice` |
| `b-pool-dbslow` | B사 | 풀 축소 배포 + DB 지연 | 직전 변경이 있으니 풀 고갈을 증상으로 보지 않음. 처리할 원인 RB-STD-01 → 롤백이 계약상 불가 → `ACTION_BLOCKED` 에스컬레이션 → 보고서. 후보에 RB-STD-05가 함께 있고 보고서에 남는다 |
| `a-dbslow-backlog` | A사 | DB 지연 + 트래픽 급증(부하 발생기) | 데모 앱은 의존 호출을 처리 슬롯 밖에서 해서 DB p95가 요청 p95에서 차지하는 비율이 그때그때 다르다. 그래서 진단이 받은 사실 표의 비율로 기대값을 정한다: 0.5 이상이면 대기열은 DB 지연의 증상 → 처리할 원인 RB-STD-05 → DBA 에스컬레이션. 미만이면 두 원인 모두 독립 → RB-STD-03 HPA 최대치 4 PR → 다시 진단 → RB-STD-05 DBA 에스컬레이션 |

판정은 지금 시나리오와 같은 방식이다. 기대한 조치가 아니면 거절하고 실패로 기록한다. 추가 판정:

- 진단의 `원인 후보`에 기대한 후보가 모두 있고 처리할 원인이 기대와 같다 (에이전트 판단을 E2E가 판정한다)
- 조치 제안 순서가 기대와 같다(지금의 "조치 제안이 한 번이다"는 복합 시나리오에서 "기대한 횟수다"로 바꾼다)
- 같은 원인에 두 번째 조치를 제안하지 않았다
- 같은 서비스에 인시던트가 하나만 열렸다(5장)

### 7.2 묶음

복합 시나리오는 각 고객사 묶음의 끝에 둔다. 전체 실행 시간이 A사 약 9분, B사 약 4분 늘어난다. `--quick`에는 넣지 않는다. E2E 시간 단축(조용한 구간, 해제 대기)은 이 스펙의 범위가 아니다.
