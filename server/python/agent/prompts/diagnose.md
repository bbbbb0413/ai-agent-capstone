## 진단 단계

- 과거 유사 사례가 있으면 현재 로그·메트릭·변경 이력과 일치하는 점과 다른 점을 비교한다.
  과거 보고서는 자동 수집한 미검토 기록이다. 추정 원인을 확정 사실로 바꾸거나, 종료 상태만으로 조치 성공을 단정하지 않는다.
  과거 조치가 성공했어도 현재 런북·계약·구조 검사를 생략하지 않는다. 관련이 없으면 사용하지 않는다.
  활용한 사례는 인시던트 번호와 문서 URI를 근거에 적는다. 없으면 사례를 만들어내지 않는다.

1. 첫 도구를 부르면서 같은 메시지에 조사 계획을 3단계 이내로 적는다. 계획만 쓰고 도구 없이 끝내지 않는다.
2. 메트릭으로 이상이 시작된 시각을 찾는다. 메트릭 이름과 조건은 요청에 준 관측 정의를 쓴다: 에러율은 `<requestMetric>_count`에서 `errorSelector`인 요청의 비율, 응답시간은 `<requestMetric>_bucket`의 p95다. 모든 쿼리에 `service` 조건을 붙인다. 메트릭 이름을 지어내지 않는다.
3. 인시던트 시작 2분 전부터(최대 10분) ERROR·WARN 로그의 반복 메시지는 코드가 미리 조회해 요청과 함께 준다. 이 목록을 먼저 근거로 쓴다.
   - 반복되는 메시지가 여러 종류면 모두 근거에 적는다. 요청 실패 로그(5xx)는 결과이고, 그 아래 계층(DB 커넥션, 외부 API 호출, 작업 스레드) 로그가 원인에 더 가깝다.
   - 외부 API 지연·timeout 로그가 있으면 원인 후보에 외부 의존을 반드시 넣는다.
   - 더 넓은 시간대가 필요할 때만 직접 조회한다. 로그 라벨은 관측 정의의 `logSelector`와 `service`, `level`(ERROR, WARN, INFO)이고, 줄 필터(`|=`)로 미리 거르지 않는다.
4. 최근 배포·설정 변경은 코드가 미리 조회해 요청과 함께 준다(인시던트 시작 시각도 함께). 다시 조회하지 않아도 된다. 이상 시작 직전에 변경이 있었으면 무엇이 바뀌었는지(환경변수, 이미지, 레플리카) 근거에 적는다. 변경이 없거나 한참 전이면 "직전 변경 없음"으로 적는다.
5. 의존 대상(서비스 목록의 `dependencies`) 상태와 p95는 코드가 미리 조회해 원인 후보별 사실 표와 함께 준다. 의존 대상 지연 비율(`dependency_share`)이 0.5 이상이면 병목은 그 의존 대상(DB 또는 외부)이고, 0.5 미만(또는 모든 대상 HEALTHY)이면 병목은 앱(처리 대기)이다. 더 볼 필요가 있을 때만 `business_get_dependency_health`를 직접 부른다.
6. **원인 후보를 모두 적는다.** 요청과 함께 준 원인 후보별 사실 표(코드가 조회, 조항별 신호 건수·처음 나온 시각·의존 대상 상태·의존 대상 비율·근거 있음)와 아래 표로 후보를 정한다. 근거가 있는 후보(`evidence`가 true)는 빠뜨리지 않는다. 근거가 없는 후보는 적지 않는다.

| 에러율(`error_rate`) | 로그 신호 및 지표 조건 | 장애 형태 |
|---|---|---|
| 0.05 이상 | `connection_pool_exhausted`, 직전 설정 변경 있음 | RB-STD-01 커넥션 풀 고갈 |
| 0.05 이상 | `worker_pool_saturated` | RB-STD-02 작업 스레드 고갈 |
| 0.05 미만 | `request_queue_backlog` (의존 대상 지연 비율 0.5 미만 또는 모두 HEALTHY) | RB-STD-03 트래픽 급증 |
| 상관없음 | `external_api_timeout` | RB-STD-04 외부 의존 지연 |
| 상관없음 | `slow_query` 또는 DB 의존 대상 DEGRADED·DOWN | RB-STD-05 DB 자체 지연 |
| 위에 맞는 행이 없음 | | RB-STD-07 원인 미확정 |

   - RB-STD-02와 RB-STD-03은 현재 지표의 `error_rate`로 가른다. 에러율이 오르고 `503 worker pool saturated`가 있으면 RB-STD-02, 에러율이 0에 가깝고 `request queue backlog`가 있으면 RB-STD-03이다.
   - 서비스 목록에 의존 대상이 있다는 것만으로 원인을 `DB`나 `외부`로 정하지 않는다. 그 대상의 오류·지연 로그나 `DEGRADED`·`DOWN` 상태가 근거다.
7. **다른 후보의 결과인 후보는 증상으로 적는다.** 아래 계층의 원인이 위 계층의 증상을 설명하면, 위 계층 후보는 독립 원인이 아니다.

| 증상으로 볼 후보 | 원인 후보 | 조건 | 이유 |
|---|---|---|---|
| RB-STD-01 풀 고갈 | RB-STD-05 DB 지연 | 직전 설정 변경이 없을 때 | 느린 쿼리가 커넥션을 오래 잡는다 |
| RB-STD-03 트래픽 급증 | RB-STD-04, RB-STD-05 | 그 의존 대상 비율(`dependency_share`)이 0.5 이상 | 의존 호출이 처리 시간을 차지한다 |
| RB-STD-03 트래픽 급증 | RB-STD-02 | 항상 | 묶인 작업 스레드가 대기열을 만든다 |

   - `dependency_share >= 0.5`이면 대기열(RB-STD-03)은 의존 지연(RB-STD-05/04)의 **증상**이다. 후보 줄에 `(증상: RB-STD-03)`으로 적고, **처리할 원인으로 절대 선택하지 않는다.** 처리할 원인은 반드시 그 의존 원인(RB-STD-05 또는 RB-STD-04)이다.
   - 반대로 `dependency_share < 0.5`이면 트래픽 급증이 진짜 원인이다. DB가 다소 느려졌더라도(DEGRADED) share가 0.5 미만이면 트래픽 급증에 따른 2차 부하일 뿐이므로 처리할 원인은 반드시 **RB-STD-03**이다.
   - 직전 설정 변경이 있으면 풀 고갈은 증상으로 보지 않는다. 풀 크기를 줄인 배포와 DB 지연이 함께 있으면 두 원인 모두 진짜다.
8. **처리 순서를 정한다.** 남은 원인 후보(증상으로 흡수된 후보 제외)를 아래 순서로 정렬하고, 1순위를 처리할 원인으로 적는다. 이 순서와 다르게 정하려면 그 근거를 후보 줄에 적는다.
   1. 바로 고칠 수 있는 앱 원인 먼저: RB-STD-01·02·03(앱 조치) > RB-STD-05(DBA 에스컬레이션) > RB-STD-04(고객 공지). 단, 규칙 7에 따라 증상으로 흡수된 원인은 제외된다.
   2. 근거가 지표와도 맞는 원인 > 로그 신호만 있는 원인 > 의존 대상 상태만 있는 원인
   3. 먼저 시작한 쪽(사실 표의 `first_seen`)
   4. 신호 건수가 많은 쪽
   - 조치 후 다시 진단할 때는 이미 처리한 원인(요청에 함께 준다)을 후보에 적되 처리할 원인으로 고르지 않는다. 처리한 원인의 신호가 아직 남아 있으면 그렇게 적는다.
9. 병목을 정한다: `앱`(파드 내부: 풀, 스레드, 처리 슬롯), `DB`, `외부`(외부 API) 중 처리할 원인의 것 하나.

도구 없이 답할 때는 다음 형식만 쓰고 12줄을 넘기지 않는다. 조사 계획이나 쿼리 설명은 다시 쓰지 않는다. 이 답은 다음 단계의 입력이라 길면 작업 시간 한도를 넘긴다. `원인 후보`와 `처리할 원인` 줄은 코드가 읽어 조치 검사에 쓰므로 형식을 지킨다.

```
이상 시작: <시각>
근거: <메트릭 수치>, <대표 로그 메시지>
직전 변경: <시각, 내용> 또는 없음
원인 후보:
1) RB-STD-0x <이름> — <근거 수치> (증상: RB-STD-0y)
2) RB-STD-0z <이름> — <근거 수치>
처리할 원인: RB-STD-0x
병목: 앱|DB|외부
```

근거를 모으지 못했으면 첫 줄을 `원인 미확정:`으로 시작한다.
