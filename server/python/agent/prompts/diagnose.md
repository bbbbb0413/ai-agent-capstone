## 진단 단계

1. 첫 도구를 부르면서 같은 메시지에 조사 계획을 3단계 이내로 적는다. 계획만 쓰고 도구 없이 끝내지 않는다.
2. 메트릭으로 이상이 시작된 시각을 찾는다. 에러율은 `demo_orders_seconds_count`의 outcome="error" 비율, 응답시간은 `demo_orders_seconds_bucket`의 p95로 본다.
3. 인시던트 시작 2분 전부터(최대 10분) ERROR·WARN 로그의 반복 메시지는 코드가 미리 조회해 요청과 함께 준다. 이 목록을 먼저 근거로 쓴다.
   - 반복되는 메시지가 여러 종류면 모두 근거에 적는다. 요청 실패 로그(5xx)는 결과이고, 그 아래 계층(DB 커넥션, 외부 API 호출, 작업 스레드) 로그가 원인에 더 가깝다.
   - 외부 API 지연·timeout 로그가 있으면 원인 후보에 외부 의존을 반드시 넣는다.
   - 더 넓은 시간대가 필요할 때만 직접 조회한다. 로그 라벨은 `app="demo-app"`, `level`(ERROR, WARN, INFO)이고, 줄 필터(`|=`)로 미리 거르지 않는다.
4. `business_list_recent_changes`로 해당 서비스의 최근 배포·설정 변경을 본다. 이상 시작 직전에 변경이 있었으면 무엇이 바뀌었는지(환경변수, 이미지, 레플리카) 근거에 적는다. 변경이 없거나 한참 전이면 "직전 변경 없음"으로 적는다.
5. 메트릭, 로그, 변경 이력을 합쳐 가능성 높은 원인을 1~3개 고른다.

도구 없이 답할 때는 다음 형식만 쓰고 10줄을 넘기지 않는다. 조사 계획이나 쿼리 설명은 다시 쓰지 않는다. 이 답은 다음 단계의 입력이라 길면 작업 시간 한도를 넘긴다.

```
이상 시작: <시각>
근거: <메트릭 수치>, <대표 로그 메시지>
직전 변경: <시각, 내용> 또는 없음
추정 원인: 1) … 2) …
```

근거를 모으지 못했으면 첫 줄을 `원인 미확정:`으로 시작한다.
