## 보고서 작성 단계

입력 JSON을 바탕으로 진단 리포트를 Markdown으로 쓴다. 입력에 없는 사실은 쓰지 않는다.

- approvals는 사람의 결정이며 실행 성공을 뜻하지 않는다. 실행 여부는 action_result로 판단한다.
- action_result.status가 FAILED면 실행 실패, UNCONFIRMED면 결과 확인 불가, EXECUTED면 조치 실행,
  SENT면 고객 공지 발송이다. 결과가 없으면 실행했다고 쓰지 않는다.
- PR_CREATED는 PR 생성만 끝난 상태다. change.result가 SYNCED일 때만 병합·동기화 완료라고 쓴다.
- 도구가 error를 반환했으면 근거 조회/조치에 실패한 것이다. 관리 API의 접속·인증 오류만으로
  고객 서비스 지연의 원인을 확정하지 않는다. 로그를 조회하지 않았으면 '미조회'라고 쓴다.
- 수치는 `evidence`의 도구 결과와 `verification`(회복 확인 결론)에서 그대로 옮긴다.
- 입력에 근거가 없는 항목은 "조회하지 않음" 한 마디만 쓴다. "확인 필요", "전달받지 못함" 같은 설명을 붙이지 않는다.
- `recovered`가 true면 현재 상태는 "정상화됨"이다. 반영 대기나 진행 중이라고 쓰지 않는다.
- `escalation`이 있으면 에스컬레이션을 발송 대기열에 넣은 것이다(status QUEUED). 실제 발송은 아직 없으므로 "호출 대기열에 등록"이라고 쓰고, 받는 사람(`recipients`)을 적는다. "호출했다", "연락했다"고 쓰지 않는다.
- `no_action_reason`이 있으면 조치를 제안하지 않은 것이다(HPA가 확장 중). 조치와 결과 절에 그 이유를 쓰고, 실행했다고 쓰지 않는다.
- `change`가 있으면 설정 저장소 PR로 반영한 것이다. PR 주소와 병합·동기화 결과(`change.result`)를 적는다. `action_result.status`가 EXECUTED면 바로 실행한 것이다.
